## 1. 业务概述与对外接口 (Overview & Public Interfaces)
- **核心目标**: 采集设备安全相关日志，提供本地查询、过滤、分页、结构化详情查看、清理、留存配置、CSV 导出和离线日志导入能力。列表、详情和导出面向用户展示稳定业务语义，不直接暴露系统审计原始 JSON、内部字段路径或无业务含义的元数据，同时保留必要的内部追溯证据。
- **入口路由 (Route Entry)**: `log-manage` -> `entry/src/main/ets/views/log-manage/overview/LogManagePage.ets`
- **对外暴露能力 (Public APIs)**:
  - 页面入口由主导航路由到 `LogManagePage`。
  - 业务层主要通过 `LogCollectorService`、`LogEntryRepository`、`LogStorageMaintenanceService`、`LogExportService`、`LogImportService` 对模块内部提供采集、存储、维护、导出和离线导入能力。
  - 当前没有面向其他业务模块的公共 SDK 或跨模块写入接口。
- **业务边界**:
  - ✅ **包含**: 系统审计日志订阅、设备开关机审计日志、崩溃日志采集、本地 RDB 存储、日志查询过滤、分页展示、结构化列表摘要、分组详情弹窗、日志清理、留存配置、结构化 CSV 导出、zip 离线日志导入、内核日志导入规则、faultlogger 崩溃日志导入规则。
  - ❌ **不包含**: 测试代码设计、测试用例说明、远端日志上报、云端审计平台、用户自定义审计规则、审计事件策略下发、系统审计框架自身能力实现、面向用户的原始载荷查看器、`remoteLog/hilog/hilog.*` 普通 hilog 文本导入。

## 2. 状态与数据流 (Data Flow & State)
> **设计原则**: 单向数据流 (View -> ViewModel -> Service -> Repository/Storage)

- **核心业务状态 (Core Business State)**:
  - `LogManageState.initialized: boolean`: 页面是否完成存储初始化、设置加载和首屏快照构建。
  - `LogManageState.loading: boolean`: 页面初始化或关键异步操作中的加载态。
  - `LogManageState.active: boolean`: 列表页是否处于活跃态；非活跃时自动刷新被跳过。
  - `LogManageState.autoRefreshEnabled: boolean`: 是否响应存储变更自动刷新。
  - `LogManageState.mode: 'list' | 'settings'`: 当前展示列表视图或存储设置视图。
  - `LogSummaryState`: 总数、过滤后数量、今日数量和当前页数量。
  - `LogFilterState`: 事件类型筛选、时间范围筛选和关键字；时间范围默认 `0` 表示“全部时间”，其它选项由展示层统一配置为最近 1 小时、最近 12 小时、最近 24 小时和最近 3 天。
  - `LogPaginationState`: 当前页、页大小、页码输入和总页数。
  - `LogListState.pagedEntries: LogEntry[]`: 当前页领域记录；页面组件必须先经展示转换层生成 `LogListItemViewData` 后渲染，不得直接展示 `detail` 或遍历结构化事实。
  - `LogDetailState`: 详情弹窗可见性和当前日志 `entryId`；弹窗打开后由展示转换层基于点击时的稳定 `LogEntry` 快照生成 `LogDetailViewData`，后续列表刷新不得污染已打开详情。
  - `LogStorageSettingsState`: 最大本地条数、留存天数、脏状态和保存态。
- **关键流转路径**:
  - 页面初始化 -> `LogManageViewModel.initialize()` -> 初始化 RDB、注册变更监听、加载设置、构建快照 -> 更新 `initialized / summary / list / pagination`，初始化失败时记录 error 日志并保持未初始化态。
  - 页面激活 -> `activate()` -> `active = true` -> 存储变更可触发 `refreshIfActive()`。
  - 切换到设置页 -> `setMode('settings')` -> 加载设置、关闭详情、暂停列表活跃态和自动刷新。
  - 修改筛选条件 -> `setEventTypeIndex()` / `setTimeRangeIndex()` / `setKeyword()` -> 重置到第一页 -> ViewModel 将时间范围选项转换为 `LogQuery.startTimestamp` -> 先计算过滤后总数，再复用该计数构建查询快照并刷新当前页。
  - 分页操作 -> `setPageSizeIndex()` / `jumpToInputPage()` / `goToPreviousPage()` / `goToNextPage()` -> 更新分页状态 -> 复用过滤后总数重建当前页列表。
  - 日志采集 -> `LogCollectorService` 从审计/崩溃/生命周期源接收 `LogEntry` -> `LogStorageMaintenanceService.appendEntries()` -> `LogEntryRepository.upsertEntries()` -> 通知 ViewModel 刷新。
  - 开关机日志采集 -> `LogAuditSource` 通过 `securityAudit` 客户端直接订阅 API26 真机安全审计配置定义的 `DEVICE_POWER_ON (0x16000001)` 与 `DEVICE_POWER_OFF (0x16000002)` -> `LogAuditEventMapper` 映射为结构化 `POWER` 日志 -> Collector 批量写入 RDB。应用生命周期、企业管理员回调和公共事件不参与开关机判断。
  - 结构化展示 -> Repository 返回 `LogEntry` -> `LogEntryPresentationMapper` 根据稳定 `eventKey` 和 `fields` 构造列表/详情展示模型 -> 组件只按展示模型渲染；Presentation 不解析系统原始 JSON，Source/Mapper 不生成中文标签、字段分组或界面布局。
  - 清理日志 -> `clearLogs()` -> `LogStorageMaintenanceService.clearAll()` -> 关闭详情并重建快照。
  - 导出日志 -> `exportLogs()` -> `LogExportService.export()` -> 查询当前过滤快照并通过 CSV 导出服务写出文件。
  - 添加日志 -> `importLogs()` -> `LogImportService.import()` / `importSelected()` -> 选择外层 zip，服务层自动使用应用私有临时工作根目录 -> `taskpool.LongTask(runLogImportPrepareTask)` 在后台解压外层 zip / 嵌套 zip、枚举文件元数据并过滤候选文件 -> `LogImportService` 顺序调度 `taskpool.execute(runLogImportFileParseTask, file)`，每个任务只调用一个可插拔规则处理当前文件，其中 `KernelLogImportRule` 过滤 `hilog/hilog_kmsg*`、按需同目录预解压 `.gz`、逐行解析内核日志，`CrashLogImportRule` 过滤 `faultlogger/*.log`、按文件解析崩溃日志，`SystemLogImportRule` 按白名单路径解析系统日志 -> `LogImportHash` 生成稳定 ID -> 当前文件结果按 1000 条分批执行过期过滤、批内去重、库内批量查重和导入专用写入 -> 每累计约 10000 条执行一次不通知页面的容量维护 -> 全部候选文件完成后统一执行留存清理、最大条数裁剪和一次存储通知 -> 刷新列表与统计 -> 无论成功、失败或异常均清理本次临时工作区。

## 3. 核心功能场景 (Core Functional Scenarios)

### 3.1 结构化浏览日志

1. 用户进入日志管理页面，通过时间、一级日志类型和关键字定位记录。
2. 列表按具体事件语义展示标题，例如“文件重命名”“应用启动”“DNS 查询”“设备关闭”，不得将所有低频事件统一显示为“审计日志”，也不得把 JSON 或原始日志正文作为标题。
3. 用户打开详情后，按“事件概览、操作对象、操作主体、影响与变更、技术信息”查看有值字段；不适用的分组和空字段不占位。
4. 文件路径、错误原因、堆栈和其它长文本完整换行并支持复制；结构化字段沿用原详情弹窗的全宽键值行，技术字段位于详情底部。
5. 原始 `content`、`metadata`、内部字段路径和原始 JSON 不进入列表、详情或普通 CSV 导出；缺少已知字段时展示事件名称与可确认的公共字段，不以原始载荷兜底。
6. 详情弹窗保持既有视觉规范：默认宽度、顶部“日志概览”灰底卡、下方“结构化详情”灰底卡、分组标题和全宽键值行；结构化改造只替换数据内容，不引入新的强调色摘要卡、多层描边、字段计数或双列小卡片。

## 4. 模块结构与组件设计 (Module Components)

### 【核心层】(Core MVVM & Domain Layers)

#### 4.1 Model & Types (核心数据模型与类型)
* **核心实体与依赖路径**:
  * `LogEventType`
    * **所在文件**: `entry/src/main/ets/models/LogModels.ets`
    * **业务作用**: 定义日志事件类型枚举。
    * **关键字段**: `CRASH`、`FILE`、`ACCOUNT`、`PERMISSION`、`POWER`、`SYSTEM`、`KERNEL`、`AUDIT`。
    * **导入说明**: `SYSTEM`、`KERNEL` 仅由离线导入链路产生，不接入 `LogCollectorService` 实时采集；`AUDIT` 由实时审计订阅链路产生，用于承接当前项目未归入文件、账号/认证、权限、崩溃等专用类型的其它 `securityAudit.NotifyEvent`。
    * **筛选值顺序**: `ALL_LOG_EVENT_TYPES` 是 ViewModel 查询映射和页面展示选项共同使用的业务顺序；展示层只能基于该数组派生 label，不得另建业务顺序。
  * `LogEntry`
    * **所在文件**: `entry/src/main/ets/models/LogModels.ets`
    * **业务作用**: 日志管理模块的稳定领域记录，是采集、存储、查询和导出的统一数据结构，但不是页面可直接渲染的 UI 模型。
    * **关键字段**: `id`、`timestamp`、`eventType`、`eventKey`、`detail`、`processName`、`pid`、`uid`、`filePath`、`remoteAddr`、`sourceEventId`、`rawEventName`、`fields`、`rawPayload`。
    * **一级类型与具体事件**: `eventType` 继续承担现有八类筛选和统计；`eventKey` 是与 SDK 数字事件 ID 解耦的稳定业务键，采用 `<domain>.<action>` 命名，例如 `file.rename`、`app.start`、`process.exit`、`network.dns`、`device.power_off`。新增审计事件不得仅依赖 `AUDIT` 类型或中文描述区分。
    * **搜索摘要**: `detail` 调整为持久化搜索投影，由具体事件名称和关键结构化字段生成，供现有 SQL 关键字查询使用；列表和详情组件不得直接渲染 `detail`，未知或缺字段事件也不得将原始载荷写入 `detail`。
    * **规范化规则**: `LogEntryNormalizer` 对搜索摘要、文件路径、远端地址、原始事件名和结构化字段做长度限制；原始动作、结果与风险值统一进入 `event.action`、`event.outcome`、`event.risk_level` 等结构化字段，不再保留 `rawAction/rawOutcome` 顶层副本。结构化字段禁止保存重复的原始 JSON、递归展开载荷或中文 UI 标签。
  * `LogField`
    * **所在文件**: `entry/src/main/ets/models/LogModels.ets`
    * **业务作用**: 保存与展示无关的结构化事实。
    * **关键字段**: `key`、`value`；`value` 只允许 `string | number | boolean`，`key` 使用稳定命名空间，例如 `object.file_path`、`actor.process_name`、`change.new_mode`、`technical.rule_id`。同一记录中的字段键必须唯一。
    * **边界约束**: 不保存 `label`、分组、排序、颜色、宽度或其它 UI 属性；数组类业务值由对应 Source Parser 归一为可读的多值文本，不以 JSON 字符串交给页面。
  * `LogRawPayload`
    * **所在文件**: `entry/src/main/ets/models/LogModels.ets`
    * **业务作用**: 可选保存一次系统来源 `content` / `metadata`，仅用于内部问题定位和后续映射校准。
    * **关键字段**: `content?`、`metadata?`、`truncated`；序列化后的总长度上限为 64 KiB，超过上限时先保留 `content`、再使用剩余额度保留 `metadata`，并设置 `truncated = true`。
    * **边界约束**: 不进入 `fields`、`detail`、列表、详情和普通 CSV 导出；不得同时保存原始 JSON、递归展开副本和结构化副本。Source 业务日志只记录事件 ID、映射结果和必要错误，不输出完整载荷。
  * `LogListItemViewData`、`LogDetailViewData`、`LogDetailSection`、`LogDisplayField`
    * **所在文件**: `entry/src/main/ets/presentation/log-manage/LogEntryPresentationModels.ets`
    * **业务作用**: 只承载页面最终需要的标题、标签、上下文、分组和字段布局，是列表及详情组件唯一消费的展示契约。
    * **边界约束**: 展示模型由纯函数基于 `LogEntry` 生成，不写回领域记录和 RDB，不携带 `rawPayload`。
  * `LogStorageConfig`
    * **所在文件**: `entry/src/main/ets/models/LogModels.ets`
    * **业务作用**: 控制本地最大日志条数和保留天数。
    * **关键字段**: `maxLocalEntries` 默认 `20000`，`retentionDays` 默认 `30`。
    * **页面默认**: 存储设置面板未收到 ViewModel 入参时必须使用 `DEFAULT_LOG_STORAGE_CONFIG.retentionDays`，不得退回到保留天数选项首项。
    * **配置选项**: 
      * 最大存储条数选项：`[5000, 10000, 20000, 50000, 100000]`，最大值 `100000`
      * 保留天数选项：`[7, 14, 30, 90, 180]`，最大值 `180`
  * `LogManageState` 与子状态
    * **所在文件**: `entry/src/main/ets/models/LogManageModels.ets`
    * **业务作用**: 页面状态树，承载摘要、筛选、分页、列表、详情和模式状态。
    * **关键字段**: `summary`、`filter`、`pagination`、`list`、`detail`、`mode`。
    * **时间筛选**: `filter.timeRangeIndex` 记录页面时间范围筛选选项，`0` 为“全部时间”，`1` 为最近 1 小时，`2` 为最近 12 小时，`3` 为最近 24 小时，`4` 为最近 3 天；非 `0` 时由 `LogManageViewModel.buildQuery()` 转换为 `startTimestamp = Date.now() - durationMs`。
  * `LogStorageSettingsState`
    * **所在文件**: `entry/src/main/ets/models/LogManageModels.ets`
    * **业务作用**: 存储设置页状态。
    * **关键字段**: `maxLocalEntries`、`retentionDays`、`dirty`、`saving`。
  * `ImportLogsCode`、`ImportLogsResult`、`LogImportSelectionResult`
    * **所在文件**: `entry/src/main/ets/models/LogImportModels.ets`
    * **业务作用**: 定义离线日志导入在 View、ViewModel 与 Service 之间共享的选择结果和导入结果契约。
    * **边界约束**: 页面和 ViewModel 只依赖模型层结果，不从 `LogImportService.ets` 导入 DTO；Picker/Workspace 端口仍由服务层持有。

#### 4.2 Service / Domain (领域业务层)
* **真实文件路径**: `entry/src/main/ets/services/log-manage`
* **核心业务用例 (Use Cases)**:
  * `LogCollectorService.start(context)`: 启动日志采集。
    * **副作用**: 初始化存储、按当前内置映射订阅全部系统审计事件、启动崩溃源、记录采集器状态。
    * **失败策略**: 审计或崩溃源失败时进入降级态，保留可用采集源。
    * **文件日志噪音过滤**: 文件类审计事件进入 `LogCollectorService.handleIncomingEntry()` 后、写入 `pendingEntries` 和 RDB 前，必须先执行内部噪音过滤。过滤范围包含本应用设置、主题、HiAppEvent、应用数据库、日志导出目录以及日志导入过程中在用户文件空间 `Docs/.Trash/.../security_log_import_*` 目录下产生的解压/扫描文件事件。该规则只影响新增文件操作日志，不迁移、不删除历史已入库记录。
  * `LogCollectorService.stop()`: 停止采集。
    * **副作用**: 取消审计订阅、停止崩溃源。
    * **失败策略**: 返回状态结果并记录错误日志。
  * `LogAuditSource.subscribe(onEntry, eventTypes?)`: 订阅系统审计事件并将审计事件映射为 `LogEntry`。
    * **副作用**: 创建 `securityAudit` 客户端、按事件逐个订阅、为文件事件挂载前缀过滤器。
    * **失败策略**: 全部失败返回 `unsupported` 或 `permission_denied`，部分失败返回 `partial`，保留已成功订阅的事件。
  * `LogStorageMaintenanceService.appendEntries(entries)`: 批量写入日志并执行维护。
    * **副作用**: 写入 RDB，按留存天数删除过期日志，按最大条数裁剪旧日志。
    * **失败策略**: 返回 `MutationResult`，由调用方决定是否刷新 UI。
  * `LogEntryRepository.listByQuery(query, limit, offset)`: 按筛选条件分页查询日志。
    * **副作用**: 无，仅查询 RDB。
    * **时间范围**: 当 `LogQuery.startTimestamp` 存在时，查询条件追加 `timestamp >= startTimestamp`；该条件与事件类型和关键字使用 `AND` 组合。
  * **失败策略**: Repository 层记录错误，日志列表查询、计数和统计失败必须向上暴露为查询失败，不得以空数组或 0 条静默伪装成功。
  * `LogEntryRepository.getStatistics()`: 统计总数、今日数量和类型分布。
    * **副作用**: 无。
    * **失败策略**: 查询失败时由上层刷新流程返回失败结果，页面保留可解释的失败态或最近一次成功状态。
  * `LogExportService.export(context, query, fileNamePrefix?)`: 导出当前查询条件下的日志。
    * **副作用**: 查询日志快照并调用公共 CSV 文件导出服务；CSV 的详情列使用结构化搜索摘要 `detail`，不导出 `rawPayload` 或字段路径。导出内容必须写入 UTF-8 BOM，所有字段统一经 CSV 转义后输出；公共导出服务必须以统一文件打开/关闭流程写入，并在覆盖同名文件时截断旧内容。
    * **失败策略**: 返回 `ExportLogsResult`，区分空数据、查询失败和写文件失败。
  * `LogImportService.import(context)`: 从用户选择的外层 zip 包导入离线日志。
    * **副作用**: 通过 Picker 选择 zip，自动使用应用私有临时工作根目录解压外层 zip、递归处理嵌套 zip、枚举解压后的文件元数据，调用导入规则生成 `LogEntry`，过滤重复记录后复用维护服务入库；导入结束后必须清理临时工作根目录。
    * **失败策略**: 区分用户取消、非法压缩包、解压失败、规则解析失败和入库失败；规则无法解析完整字段的记录直接丢弃，不入库。
  * `LogStorageSettingsViewModel.save()`: 保存存储配置。
    * **副作用**: 写入 Preferences，触发后续维护策略使用新配置。
    * **失败策略**: 保存失败保持 `dirty` 状态，便于用户重试。
* **审计事件订阅设计**:
  * **订阅入口**: `entry/src/main/ets/services/log-manage/source/LogAuditSource.ets`
  * **订阅来源**: `@kit.DeviceSecurityKit` 的 `securityAudit`。
  * **类型到审计事件映射**:

| 日志类型 | 审计事件 | 说明 |

| `LogEventType.FILE` | `securityAudit.NotifyEvent.FILE` | 文件访问事件 |
| `LogEventType.FILE` | `securityAudit.NotifyEvent.FILE_INTERCEPTED` | 文件访问被拦截事件 |
| `LogEventType.FILE` | `securityAudit.NotifyEvent.KIA_CREATE` | KIA 创建类文件事件 |

| `LogEventType.FILE` | `securityAudit.NotifyEvent.KIA_VARIANT` | KIA 变体类文件事件 |
| `LogEventType.FILE` | `securityAudit.NotifyEvent.KIA_INTERCEPT` | KIA 拦截类文件事件 |
| `LogEventType.FILE` | `securityAudit.NotifyEvent.KIA_PRE_OPEN` | KIA 文件预打开事件 |
| `LogEventType.FILE` | `securityAudit.NotifyEvent.FILE_CREATE / FILE_OPEN / FILE_CLOSE / FILE_DELETE / FILE_RENAME / FILE_COPY / FILE_SETOWNER / FILE_SETMODE / FILE_SETEXTATTR / FILE_DELETEEXTATTR / FILE_WRITE` | API26 正式文件操作枚举；全部使用 SDK 枚举并挂载用户目录前缀过滤器 |
| `LogEventType.ACCOUNT` | `securityAudit.NotifyEvent.ACCOUNT` | 账户事件 |
| `LogEventType.PERMISSION` | `securityAudit.NotifyEvent.PERMISSION` | 权限事件 |
| `LogEventType.POWER` | `0x16000001 / 0x16000002` | API26 真机安全审计配置中的 `DEVICE_POWER_ON / DEVICE_POWER_OFF`；SDK `NotifyEvent` 尚未导出名称，按设备正式事件配置订阅 |
| `LogEventType.AUDIT` | 其余低频官方 `securityAudit.NotifyEvent` | DNS/网络拦截、窗口、移动存储、文件分享、数据拖拽、DLP 文件访问、应用、EDM、代码签名、证书、应用拦截、进程与内核异常、剪贴板、HDC、摄像头、打印、跨用户数据交换、USB 和串口等事件；`NETWORK_TRAFFIC`、`NETWORK_CONN` 仍因高频日志风暴排除 |

  * **补充来源说明**: `CRASH` 同时包含 `LogCrashSource` 的 hiAppEvent 崩溃采集和官方 `PROCESS_CRASH_ABNORMAL` 审计事件。`POWER` 直接订阅真机 `/system/etc/security_guard_event_ext.json` 定义且 `/system/etc/security_audit_ext.cfg` 已配置采集的 `0x16000001 / 0x16000002`；不再通过 `LogPowerLifecycleSource`、企业管理启动回调或 `usual.event.SHUTDOWN` 生成。旧的 `0x27000004`、`0x27000005` 实际为认证事件，`0x2700000D` 不是电源事件，均不得用于开关机映射；`0x1C001401` 对应 `PROCESS_DEBUG_ABNORMAL` 而非崩溃。`AUDIT` 不抢占 `FILE`、`ACCOUNT`、`PERMISSION`、`POWER`、`CRASH` 的明确映射，只承接其它低频通知事件。`NETWORK_TRAFFIC` 和 `NETWORK_CONN` 继续因样机高频日志风暴而排除。
  * **API26 新事件来源**: API26 文件操作统一改用 SDK 正式枚举并完整接入 `FILE_CREATE` 至 `FILE_WRITE`；`FILE_SHARE`、`DATA_DRAG`、`DLP_FILE_ACCESS` 属于数据交换/访问审计，归入 `AUDIT` 且不挂文件路径前缀过滤器。此前因无法稳定触发而未接入的事件不再以“是否已在样机触发”作为订阅前提，订阅失败由既有 `failedEventIds` 降级机制处理。
  * **权限结论**: 普通通知客户端 `newClient/subscribe/addFilter` 及 API26 新增 `NotifyEvent` 均使用现有 `ohos.permission.QUERY_AUDIT_EVENT`。`ohos.permission.kernel.AUTH_AUDIT_EVENT` 仅用于 `AuthClient` 文件授权事件，不是普通通知事件的补充权限；本模块不创建 `AuthClient`，因此不新增该权限，也不修改签名 profile。
  * **审计事件注册表**: 以 `LogAuditEventRegistry` 作为订阅和映射的单一来源，每个定义至少包含 `eventId`、`eventType`、`defaultEventKey`、`parserKind` 和 `filterPolicy`。`LogAuditSource` 从注册表派生订阅 ID 和文件过滤要求，`LogAuditEventMapper` 从同一注册表取得默认业务键和解析器；不得继续分别维护事件 ID 数组、类型 Map、中文说明 Map 和订阅 Map。
  * **注册表职责边界**: Source 注册表只保存系统枚举、稳定业务键、解析类型和过滤策略，不保存中文标题、详情分组或页面字段顺序。中文语义统一由 Presentation 的 `LogEventDisplayRegistry` 维护。
  * **事件解析器**: `LogAuditEventMapper` 只负责公共时间、用户、事件 ID、注册表查找和分类分派；文件、账户、权限、电源及通用审计分别由类别级纯解析器返回最终 `eventKey + LogField[]`。`APP`、`PROCESS`、`EDM` 等包含子类型的事件可根据已验证字段细化默认业务键，字段缺失时使用注册表 `defaultEventKey`。不得为每个事件建立独立类，也不得继续在单个大 `switch` 中同时处理系统载荷、中文标签、列表摘要和详情布局。
  * **结构化字段规则**: Source Parser 只抽取已知且具有业务语义的字段；未知字段保留在可选 `rawPayload` 中，不递归生成 `audit.content.*` / `audit.metadata.*` 字段，不把数组或对象序列化为原始 JSON 展示值。字段缺失时直接省略，不生成“未知”“-”“空”等占位值。
  * **审计展示规则**: `LogEntryPresentationMapper` 根据 `eventKey` 和 `fields` 生成具体事件标题及分组详情。`APP` 的已验证 `subType=0/1` 映射为 `app.start/app.exit`，`PROCESS` 的已验证 `subType=2/-1` 映射为 `process.create/process.exit`；DNS、EDM、权限提升、摄像头、打印、USB 等事件分别使用稳定业务键，不再统一显示为“审计日志”。
  * **EDM 审计语义**: Source Parser 保存 `edm.object_info` 与 `edm.operation_type` 原始业务值；Presentation 将已验证 `objectInfo` 映射为中性中文对象名称，将 `type=0/1` 映射为“读取/查询策略状态”“设置/变更策略状态”。未知对象值直接作为操作对象展示，未知 `type` 展示为 `type=N`，但不得回退展示整段载荷，也不得将 `type=1` 推断为用户手动操作。
  * **搜索摘要规则**: `detail` 由 `eventKey` 对应事件名称和少量关键字段生成，仅用于关键字查询。例如文件事件使用“动作 + 目标路径 + 进程”，应用/进程事件使用“动作 + 应用或进程”，EDM 使用“对象 + 操作类型”。摘要不得包含原始 JSON、字段路径或未解析的系统正文。
  * **文件审计路径解析**: `LogAuditEventMapper` 必须只保留一个文件审计路径解析入口，统一产出 `primaryPath`、`oldPath`、`newPath`。`primaryPath` 同时写入 `LogEntry.filePath` 和键为 `object.file_path` 的 `LogField`，用于列表搜索、导出数据源和详情展示的一致口径；不得在字段构造时另写一套路径优先级。路径归一化继续复用 `LogPathUtils.normalizePathCandidate()`，将 `/data/service/el2/{userId}/hmdfs/account/files/Docs/Download|Documents|Desktop/...` 转为 `/storage/Users/currentUser/...`；结构化审计字段中的路径必须保留文件名内部空格，例如 `新建 文本文档.txt` 不得被截断。
  * **文件重命名路径语义**: 当文件审计事件同时包含旧路径和新路径时，`primaryPath` 取目标/新路径，结构化字段保存 `object.file_path = primaryPath`、`change.old_path = oldPath`、`change.new_path = newPath`。典型来源字段包括 `file_oldpath` / `file_newpath`、`oldPath` / `newPath`、`srcPath` / `targetPath|dstPath`。普通文件事件只有 `file_path`、`filePath` 或 `path` 时，`primaryPath` 保持该直接路径语义。
  * **API26 文件字段**: 文件事件按业务键保存操作、主路径、原路径、新路径、进程、PID、UID、事件时间和事件 ID。对 `file_mode`、`file_newmode`、`file_owneruid`、`file_ownergid`、`file_newuid`、`file_newgid`、`file_xattrname`、`file_size` 采用“有值才保存”的结构化规则；Presentation 负责将权限模式、文件大小和官方事件名称格式化为用户可读内容。
  * **路径单一真相源**: `LogEntry.filePath` 与键为 `object.file_path` 的 `LogField` 必须来自同一个 `FileAuditPathInfo.primaryPath`。实现时删除旧的详情路径 fallback、独立原始路径解析函数和 `detailRows` 路径副本，避免列表搜索与详情展示再次分叉。
* **开关机生命周期设计**:
  * **启动日志**: 审计事件 `0x16000001` 映射为 `LogEventType.POWER` / `eventKey=device.power_on`，`rawEventName = DEVICE_POWER_ON`；详情只展示事件名称、发生时间、用户 ID 和事件 ID，原始 `content` / `metadata` 如需留存只进入内部 `rawPayload`。
  * **关机事件**: 审计事件 `0x16000002` 映射为 `LogEventType.POWER` / `eventKey=device.power_off`，`rawEventName = DEVICE_POWER_OFF`；不再依赖应用进程能否收到公共事件，也不使用下次启动推断或补偿伪造关机时间。
  * **事件时间**: 开关机事件优先使用审计载荷 `content.happenTime` 作为日志时间；`AuditEvent.timestamp` 是 sticky 事件投递时间，不能替代真实开关机发生时间。载荷缺失 `happenTime` 时才使用统一审计时间解析逻辑。
  * **sticky 去重**: 安全审计服务会在客户端重新订阅时回放最近的开关机 sticky 事件。仓储初始化时按 `event_type + timestamp(happenTime) + sourceEventId + uid` 清理既有重复项并建立 POWER 审计唯一索引；同一次开机或关机只能保留一条，不同 `happenTime` 的多次真实重启必须分别保留。
  * **离线类型说明**: `KERNEL` 不走 `securityAudit.NotifyEvent` 订阅，只由“添加日志”离线导入产生；`CRASH` 既可由运行时 `LogCrashSource` 采集，也可由“添加日志”解析 `faultlogger` 离线文件产生；`SYSTEM` 由“添加日志”按白名单系统日志规则离线导入产生。
* **离线导入设计**:
  * **入口**: `entry/src/main/ets/views/log-manage/overview/LogManagePage.ets` 在“导出日志”旁提供“添加日志”按钮；页面先完整 `await LogManageViewModel.pickImportTargets(context)`。拿到 zip 路径和默认 `targetDirectory` 并确认选择成功后，通过页面 `UIContext.getPromptAction().openCustomDialog()` 打开不依赖页面组件作用域的全局自定义弹框，并复用 `CommonLoadingDialog` 提取出的 `CommonLoadingContent`；`CommonLoadingContent` 完整绘制卡片背景、圆角和阴影并覆盖透明宿主，只呈现一层加载框。加载框沿用 `PromptAction` 默认弹框宽度，与随后由系统 AlertDialog 展示的导入成功/失败结果框保持一致；提示文字使用当前主题的主文字色并保持完整不透明度。等待全局弹框打开成功后，再执行 `LogManageViewModel.importSelectedLogs(archivePath, targetDirectory)`。不预创建组件级 controller，不增加渲染等待或失败兜底；加载框接收当前 `ThemeMode`，保持深浅色样式一致，模态遮罩覆盖应用左侧导航栏、顶部标题栏和日志内容区，导入期间不可穿透操作底层页面。
  * **线程模型**: Picker、窗口级模态等待遮罩、结果弹窗、过期过滤、库内重复过滤、RDB 入库和页面刷新保留在主线程；zip 解压、嵌套 zip 枚举和候选文件过滤由 `@Concurrent` 的 `runLogImportPrepareTask` 后台连续任务执行，单个候选文件的 gzip 解压、日志读取和规则解析由 `@Concurrent` 的 `runLogImportFileParseTask` 执行。准备任务只返回候选文件元数据，单文件任务只返回当前文件结果，禁止合并并返回整个压缩包的 `LogEntry[]`，避免超过 TaskPool 单次 16 MB 序列化限制。
  * **职责边界**: `LogImportService` 负责导入用例编排、Picker 选择、准备任务与单文件解析任务调度、单文件结果分批持久化、过期过滤、库内批量重复过滤和统计收敛；不直接持有或调用 `LogArchiveExtractor`、`LogImportRule`、`KernelLogImportRule`、`CrashLogImportRule`、`SystemLogImportRule`。`LogImportBackgroundTask` 提供准备任务和单文件解析任务：准备任务负责 zip 解压、嵌套 zip 枚举和候选文件过滤，单文件任务负责选择既有规则并解析当前文件；不得持有跨文件解析结果。
  * **任务粒度**: 外层 zip 与嵌套 zip 的准备阶段使用 `taskpool.LongTask`，并在成功、失败或异常后统一调用 `taskpool.terminateTask()`；候选文件按稳定扫描顺序串行提交普通 TaskPool，前一个文件完成解析和持久化后才处理下一个文件，不并行积压多个文件结果。
  * **持久化批次**: 单文件解析结果固定按 1000 条切分。每批先按当前留存配置的自然日 cutoff 过滤过期记录，再用当前批次 `Set` 去重，并由 `LogEntryRepository.findExistingEntryIds()` 一次查询库内已有 ID；剩余记录通过导入专用 `INSERT OR IGNORE` 事务写入，禁止逐条调用 `hasEntry()`，禁止使用 `INSERT OR REPLACE` 覆盖已有确定性 ID 记录。
  * **导入维护**: `LogStorageMaintenanceService.appendImportBatch()` 只规范化和写入当前批次，不执行留存维护、不通知页面；每累计约 10000 条成功提交记录执行一次不通知页面的过期清理与最大条数裁剪，全部文件完成后再执行一次带通知的最终维护。该增量裁剪用于将数 GB 多文件日志包导入期间的数据库规模限制在配置上限附近，页面只接收一次最终存储通知。
  * **导入统计**: `parsedEntryCount` 为各单文件规则产出数量之和；`insertedEntryCount` 为通过过期和重复过滤后成功提交写入的数量；`skippedDuplicateCount` 汇总批内、前序批次、前序文件和库内已有记录；`skippedExpiredCount` 汇总入库前被留存 cutoff 排除的记录。定期容量裁剪不回减 `insertedEntryCount`，保持其“成功提交入库”而非“最终数据库净增长”的现有语义。
  * **外层格式**: 用户 Picker 选择的外层压缩包仅支持 `.zip`；生产代码不得硬编码开发机 demo 路径，只使用 Picker 返回路径。
  * **临时工作区**: `LogImportService` 使用 `context.filesDir/log_import_tmp` 作为默认临时工作根目录，不再要求用户选择解压位置。每次导入前先清理该根目录下历史残留；`LogArchiveExtractor` 继续在根目录下创建 `security_log_import_<timestamp>` 子目录承载本次解压内容。
  * **清理要求**: `LogImportService.importSelected()` 必须在 `finally` 中清理本次传入的临时工作根目录。导入成功、解析失败、入库失败或异常退出后均必须执行清理；清理失败只记录错误日志，不覆盖导入主结果。
  * **解压规则**: `LogArchiveExtractor` 只负责解压外层 zip、递归处理嵌套 zip、枚举文件元数据；嵌套 zip 解压目录固定为 `<zipPath>_extracted`。`LogArchiveExtractor` 不读取日志全文，不判断 `hilog_kmsg*`，也不处理 `.gz` 日志载体。
  * **安全策略**: 解压时拒绝 `../`、绝对路径和逃逸目标目录的条目，避免路径穿越。
  * **规则端口**: `LogImportRule` 定义可插拔导入规则，输入解压后的文件元数据，输出 `LogEntry[]`、丢弃数和失败数；规则自行判断是否能处理该文件。
  * **内核规则**: `KernelLogImportRule` 只处理解压后 `hilog` 目录下文件名以 `hilog_kmsg` 开头的文件；若载体文件名带 `.gz`，按剥离 `.gz` 后的逻辑文件名判断，并将 `.gz` 按块解压到所在目录的同名去 `.gz` 文本文件后逐行解析。
  * **内核内存与调度策略**: `KernelLogImportRule` 不将完整 `.gz` 或完整文本文件读入内存，不对全文执行 `split()`；解析时按块/按行处理，命中规则后才构造 `LogEntry`。大文件解析必须按固定行数批次让出事件循环，避免在 UI 主线程连续执行字符串解析触发 `THREAD_BLOCK_6S`。
  * **内核热路径策略**: `parseModulePrefix`、正文规范化等逐行高频逻辑优先使用轻量字符串扫描，避免在大日志批量导入中频繁执行全局正则替换。
  * **内核文件偏移策略**: `fileIo.readSync/writeSync` 按文件偏移读写时必须维护累计 `readOffset/writeOffset`；禁止在循环中固定传入 `offset: 0`，避免反复读写同一 64KB 分片导致解压文件被覆盖或解析循环无法结束。
  * **内核诊断日志策略**: 导入链路只输出批次级、文件级和进度级日志，不逐行输出。日志至少包含导入批次 ID、候选文件数、当前规则和文件、`.gz` 解压字节进度、解析字节/行数/命中/丢弃进度、去重数量、入库数量和耗时，便于从设备日志定位卡在选择、解压、解析、去重或入库阶段。
  * **内核行过滤**: 仅处理包含 `comm=` 的行；不含 `comm=` 的行直接丢弃。
  * **内核保留规则**:

| 规则 ID | 类别 | 条件 | 结果 |
|---|---|---|---|
| `kernel_hmseh_denied` | 安全访问控制拒绝 | `modulePrefix == hmseh` 且包含 `avc: denied` 且包含 `permissive=0` 且不包含 `path="/sys/power/last_sr"` | 导入 |
| `kernel_binder_perm_failed` | Binder/IPC 权限失败 | `modulePrefix == binderfs_write` 且包含 `translate_binder failed` 且包含 `err=E_HM_PERM` | 导入 |
| `kernel_hmdec_rule` | DEC 规则设置 | `modulePrefix == hmdec` | 导入 |
| `kernel_fs_devfs_dec` | DEC 设备文件事件 | `modulePrefix == fs_devfs` | 导入 |

  * **确定性 ID**: `LogImportHash` 基于 `eventType + rawEventName + normalizedDetail` 生成稳定 `LogEntry.id`；来源压缩包、来源文件、行号、时间、PID、UID 不参与 hash，因此相同正文不同来源视为重复。
  * **崩溃规则**: `CrashLogImportRule` 只处理解压后 `faultlogger` 目录下文件名匹配 `appfreeze-*.log`、`jscrash-*.log`、`cppcrash-*.log` 的文本文件；一个 faultlogger 文件只生成一条 `LogEventType.CRASH` 记录，不按堆栈行拆分多条日志。
  * **崩溃字段映射**: 崩溃规则从文件名和文本头部抽取 `crashType`、`processName`、`pid`、`uid`、`timestamp`、`reason`、`errorName`、`errorMessage`、`stringId` 和首个有效堆栈摘要。`detail` 只保存可搜索短摘要，完整文件不写入数据库；`fields` 保存来源文件、崩溃类型、原因、错误名称、错误消息、STRINGID、Top stack 等结构化事实；不再派生 `rawOutcome = freeze/crash`。
  * **崩溃确定性 ID**: 崩溃导入 ID 基于 `eventType + crashType + processName + crashTimestamp + reason摘要 + topStack摘要` 生成；来源压缩包、来源文件路径不参与 hash，相同崩溃内容从不同来源导入视为重复；崩溃时间参与 hash，同一应用同一原因在不同时间发生时保留为不同事件。
  * **崩溃内存与调度策略**: `CrashLogImportRule` 按块/按行读取 faultlogger 文件，仅保留搜索摘要和有限 `fields`，不将完整文件写入 `detail`。解析多个大文件时按固定行数批次让出事件循环，避免阻塞 UI 主线程。
  * **系统日志规则**: `SystemLogImportRule` 严格按白名单路径处理系统日志，不处理 `remoteLog/hilog/hilog.*`。路径匹配统一转小写并将 `\` 归一为 `/`。
  * **系统日志处理范围**:

| 路径规则 | 系统日志类型 | 切分规则 |
|---|---|---|
| `remoteLog/eventlog/SERVICE_TIMEOUT_WARNING-*.log` | 服务超时异常 | 1 文件生成 1 条 `LogEntry` |
| `remoteLog/eventlog/WINDOW_EXCEPTION_DETECTION-*.log` | 窗口异常检测 | 1 文件生成 1 条 `LogEntry` |
| `remoteLog/hisi_logs/hisi_diaginfo.log` | 硬件/SoC 诊断 | 每条 `Time [...]` 生成 1 条 |
| `remoteLog/f2fs-tools/fsck.log` | 文件系统检查 | 每个 `=== yyyy/MM/dd HH:mm:ss ===` 段生成 1 条 |
| `remoteLog/f2fs-tools/resize.log` | 文件系统扩容/维护 | 每个 `=== yyyy/MM/dd HH:mm:ss ===` 段生成 1 条 |
| `remoteLog/memory/proc_meminfo*.txt` | 内存资源快照 | 1 文件生成 1 条摘要 |
| `remoteLog/memory/proc_memview*.txt` | 内存视图快照 | 1 文件生成 1 条摘要 |
| `remoteLog/memory_leak/*.txt` | 内存泄漏诊断 | 1 文件生成 1 条报告摘要，低价值短文件丢弃 |
| `remoteLog/updater/updater_log` | 系统升级/恢复日志 | 命中关键行时每行生成 1 条 |
| `remoteLog/updater/updater_stage_log` | 系统升级阶段日志 | 命中关键行时每行生成 1 条 |
| `remoteLog/log/sys_installer.log` | 系统安装/参数更新日志 | 命中关键行时每行生成 1 条 |
| `remoteLog/log/HSLd.log` | 系统服务启动/挂载日志 | 命中关键行时每行生成 1 条 |

  * **系统关键行规则**: 仅用于 `updater_log`、`updater_stage_log`、`sys_installer.log`、`HSLd.log`。空行、纯分隔符行、长度小于 8 的行丢弃；仅包含错误、告警、失败、成功、升级阶段、恢复模式或非零返回码等关键语义的行生成 `SYSTEM` 记录，普通 `INFO/I` 行只有包含关键语义时才保留，不设置单文件命中上限。
  * **系统 memory_leak 保留规则**: `remoteLog/memory_leak/*.txt` 满足任一条件才保留：包含 `Timestamp:`；包含 `Pid:`；包含 `LOGGER_MEMCHECK`；包含 `memoryName:` 且文件行数不少于 20；文件名或内容包含 `smaps` / `leakstack` / `sample` 且有有效进程名或内存名。否则丢弃。
  * **系统字段映射**: 系统日志统一写入 `eventType = SYSTEM`，`eventKey = system.<ruleId>`，`filePath = file.relativePath`，`rawEventName = 事件名或规则 ID`，`processName = PROCESS_NAME / 日志 tag / 模块名 / 文件来源`，`detail = 200-300 字可搜索短摘要`，`fields` 保存系统日志类型、来源文件、规则 ID、时间和片段摘要等结构化事实。
  * **系统结果语义**: 日志管理不维护全局结果字段；系统日志关键词仅用于识别关键行，不再映射或展示成功、失败、告警等全局结果类型。
  * **系统时间优先级**: 日志内容完整时间 -> 文件名时间 -> 段落标题时间 -> 内容中的 `MM-dd HH:mm:ss(.SSS)` 按兜底年份补齐 -> `fileIo.stat(file.path).mtime` 归一化毫秒 -> 当前导入时间。文件名时间兼容已有崩溃日志的 `yyyyMMddHHmmssSSS`，并补充系统日志常见的 `yyyyMMddHHmmss`；`mtime` 进入业务前必须统一为毫秒，避免秒级时间戳被当作毫秒写入后触发过期清理。
  * **系统无年份时间补齐**: `updater_log`、`updater_stage_log`、`sys_installer.log` 等关键行日志常见 `MM-dd HH:mm:ss(.SSS)` 格式，解析时使用兜底时间所在年份补齐；若补齐后的时间明显晚于兜底时间，则回退到上一年，避免跨年日志排序到未来。
  * **系统确定性 ID**: 系统日志导入 ID 基于 `eventType + rawEventName/ruleId + timestamp + normalizedDetail` 生成；来源压缩包和来源文件路径不参与 hash，避免相同内容不同来源重复入库；时间参与 hash，保留同类系统事件在不同时间的多次发生。
  * **系统内存与调度策略**: `SystemLogImportRule` 按块/按行读取文件，分段时只保留当前段摘要和必要字段，不把大文件全文写入 `detail`；解析大文件按固定行数批次让出事件循环。
  * **导入审计副作用**: 导入 zip、解压、读取 `faultlogger` 和 `hilog` 文件可能触发系统文件操作审计事件；该副作用属于系统审计链路的真实事件，本模块不屏蔽导入目录产生的文件操作日志。
  * **导入 IO 异常边界**: 离线导入中的 `fileIo`、`zlib`、gzip 和 UTF-8 解码调用必须在导入层显式捕获并转换为导入规则失败或解压失败结果；文件关闭或 gzip 关闭失败只记录 `warn`，不得覆盖正在传播的读取、解压或解析失败。分块读取 UTF-8 文本时必须使用流式解码，避免多字节字符跨 chunk 边界后产生替换字符。
  * **gzip 解压目标策略**: 内核 `.gz` 文件解压到导入目录下的唯一临时文本文件，解析完成后清理该临时文件；禁止无校验复用同名明文文件，避免 zip 同时包含 `.gz` 和同名文本时解析错源。
  * **导入分类顺序**: 后台解析任务先对规则解析得到的记录按确定性 ID 做批内去重，并返回批内重复数量；主线程收到解析结果后继续按“过期跳过 -> 库内重复 -> 新增”分类。过期判断使用当前日志存储配置的 `retentionDays` 和 `LogStorageMaintenanceService.buildLogStorageNaturalDayCutoff()` 的自然日 cutoff；库内重复调用 `LogEntryRepository.hasEntry(id)` 判断。
  * **过期处理**: `timestamp < cutoff` 的离线日志在入库前跳过，不调用 `LogStorageMaintenanceService.appendEntries()`，不计入新增，计入 `skippedExpiredCount`。该口径避免导入服务先计新增、随后维护服务按留存策略删除而导致 UI 新增数量虚高。
  * **重复处理**: 后台解析任务先按 ID 做批内去重；导入服务收到去重后的解析结果后过滤过期记录，再调用 `LogEntryRepository.hasEntry(id)` 过滤历史已存在记录；重复记录不调用入库链路，不更新数据库。
  * **单测口径**: `LogImportService` 单测聚焦 Picker 取消/成功、后台解析结果持久化、批内重复统计透传、过期跳过、库内重复跳过和入库失败统计；规则解析行为由 `KernelLogImportRule`、`CrashLogImportRule`、`SystemLogImportRule` 等规则单测，以及后台任务/实机验收覆盖。
  * **结果反馈**: 导入结束后返回解压文件数、扫描文件数、识别条数、新增条数、重复跳过条数、过期跳过条数、丢弃条数和失败条数，并刷新列表与统计；UI 成功提示只展示“日志添加成功”，不展示统计明细。导入统计明细继续通过后台日志输出，至少保留新增、重复跳过、过期跳过、丢弃和失败等诊断字段，便于后续排障。导入 demo 包后，系统日志应能留存 `system_updater_log`、`system_updater_stage`、`system_installer` 等关键行类记录。
* **文件事件前缀过滤器设计**:
  * **挂载事件**: 挂载到 `FILE` 类型对应的全部审计事件，包括既有 `FILE`、`FILE_INTERCEPTED`、`KIA_CREATE`、`KIA_READ`、`KIA_VARIANT`、`KIA_INTERCEPT`、`KIA_PRE_OPEN`，以及 API26 `FILE_CREATE`、`FILE_OPEN`、`FILE_CLOSE`、`FILE_DELETE`、`FILE_RENAME`、`FILE_COPY`、`FILE_SETOWNER`、`FILE_SETMODE`、`FILE_SETEXTATTR`、`FILE_DELETEEXTATTR`、`FILE_WRITE`。
  * **过滤器类型**: `securityAudit.FilterType.FILE_PATH_PREFIX`。
  * **过滤器语义**: `isInclude = true`，只接收指定路径前缀下的文件审计事件。
  * **前缀来源**: `LogAuditSource.prepareFileFilterContext()` 获取前台系统用户 ID，再调用 `LogPathUtils.buildHmdfsAccountFilesPrefix(userId)`。
  * **前缀格式**: `/data/service/el2/{foregroundUserId}/hmdfs/account/files/`。
  * **用户 ID 获取**: `osAccount.getAccountManager().getForegroundOsAccountLocalId()`；获取失败时回退 `DEFAULT_FOREGROUND_USER_ID = 100`。
  * **典型值**: 当前用户为 `100` 时，过滤前缀为 `/data/service/el2/100/hmdfs/account/files/`。
  * **挂载顺序**: 每个文件审计事件先 `client.subscribe([eventId])`，再 `client.addFilter(eventId, filter)`；若过滤器挂载失败，会立即取消该事件订阅并将该事件计入失败列表。
  * **失败策略**: 文件过滤上下文不可用、客户端无 `addFilter`、或系统返回 `FILE_FILTER_UNSUPPORTED_CODE = 1012000005` 时，该文件事件不进入有效订阅；若仍有其他事件成功，整体返回 `partial`。

#### 4.2.1 Structured Presentation Contract (结构化展示契约)

* **字段命名与唯一性**:
  * 事件概览使用 `event.action`、`event.outcome`、`event.risk_level`、`event.duration` 等键；仅在来源明确返回时保存 outcome/risk，不派生全局结果。
  * 操作对象使用 `object.application`、`object.bundle_name`、`object.process_name`、`object.file_path`、`object.user_name`、`object.domain`、`object.device`、`object.policy` 等键。
  * 操作主体使用 `actor.application`、`actor.bundle_name`、`actor.process_name`、`actor.user_name` 等键。
  * 影响与变更使用 `change.old_path`、`change.new_path`、`change.old_mode`、`change.new_mode`、`change.permission_name`、`change.permission_state`、`change.owner_uid`、`change.owner_gid` 等键。
  * 技术信息使用 `technical.source_file`、`technical.rule_id`、`technical.line_number`、`technical.string_id` 等键。`timestamp`、`pid`、`uid`、`sourceEventId`、`rawEventName` 等已有 `LogEntry` 公共字段由 Presentation 直接生成技术信息，不在 `fields` 重复保存。
  * 同一业务事实只允许一个稳定字段键；Source Parser 在入库前按键去重，Presentation 再按显示定义选择字段，不通过比较中文标签或字符串值去重。
* **列表契约**:
  * 固定展示时间、具体事件标签、主标题和最多一行关键上下文。
  * 具体事件标签由 `eventKey` 决定，例如“文件重命名”“应用启动”“DNS 查询”；一级 `eventType` 只用于筛选和统计，不直接替代具体事件标签。
  * 主标题优先使用操作对象，例如文件名/路径、应用或进程、用户名、域名、设备或策略对象；上下文只组合明确有值的进程、PID、UID、动作等字段。
  * 列表不得直接渲染 `LogEntry.detail`，不得出现以 `{` / `[` 开头的原始 JSON、转义 JSON、系统字段路径或完整日志正文。
* **详情契约**:
  * `eventKey` 对应的事件名称、一级类型和发生时间组成详情头部。
  * 详情按“事件概览、操作对象、操作主体、影响与变更、技术信息”排序；没有字段的分组不渲染。
  * 普通短字段采用双列键值布局；文件路径、远端地址、错误原因、错误消息、堆栈和多值列表使用整行布局并完整换行，所有有效值支持复制。
  * 技术信息固定在最后，包含确实存在的 PID、UID、源事件 ID、来源文件、规则 ID、行号等；不展示 `bootTime`、`tid`、`tgid`、`sid`、`pgid` 等未进入结构化字段白名单的内部值。
  * 不提供原始 JSON 展开区、原始数据开关或未知字段兜底区。
* **事件类型展示矩阵**:

| 一级类型/事件域 | 列表标题语义 | 详情结构化重点 |
|---|---|---|
| `CRASH` | 应用崩溃/冻结 + 应用或进程 | 崩溃类型、原因、错误名称、错误消息、Top stack、进程、PID/UID、来源文件 |
| `FILE` | 文件创建/打开/关闭/删除/重命名/复制/写入/属性变更 + 目标路径 | 操作、主路径、原/新路径、文件大小、权限模式、属主/属组、扩展属性、执行进程、PID/UID |
| `ACCOUNT` | 账户认证事件 + 用户 | 用户、认证方式、认证结果原值、耗时、调用方、事件时间 |
| `PERMISSION` | 权限变更 + 权限名称 | 应用、权限名称、权限状态、进程、PID/UID、事件时间 |
| `POWER` | 设备启动/设备关闭 | 发生时间、用户 ID、源事件 ID |
| `SYSTEM` | 系统事件名称 + 摘要 | 系统类别、结构化摘要、进程/模块、来源文件、规则 ID、行号 |
| `KERNEL` | 内核安全事件 + 对象/进程 | 规则类别、进程、PID/UID、文件路径、来源文件、行号 |
| `AUDIT` | 应用、进程、网络、数据交换、设备、EDM 或安全异常的具体动作 | 按 `eventKey` 选择域名、应用/进程、策略对象、设备、动作、风险原值及技术字段 |

* **专用类型业务键**:
  * 文件：`file.access`、`file.intercepted`、`file.create`、`file.open`、`file.close`、`file.delete`、`file.rename`、`file.copy`、`file.write`、`file.owner_change`、`file.mode_change`、`file.xattr_set`、`file.xattr_delete`；KIA 事件使用 `file.kia_create`、`file.kia_read`、`file.kia_variant`、`file.kia_intercept`、`file.kia_pre_open`。
  * 账户与权限：`account.authentication`、`permission.change`。
  * 电源：`device.power_on`、`device.power_off`。
  * 崩溃：`crash.runtime`、`crash.process_abnormal`、`crash.app_freeze`、`crash.javascript`、`crash.native`。
  * 离线系统与内核：使用 `system.<ruleId>`、`kernel.<ruleId>`，`ruleId` 必须来自导入规则常量且保持稳定，不使用来源文件名动态生成业务键。
* **审计子域命名**:
  * 应用与进程：`app.lifecycle`、`app.start`、`app.exit`、`process.lifecycle`、`process.create`、`process.exit`、`process.debug_abnormal`、`process.privilege_escalation`；`*.lifecycle` 只用于子类型缺失或未知时的最小语义展示。
  * 网络：`network.dns`、`network.intercepted`、`network.wifi_intercepted`。
  * 数据与文件流转：`data.smb_send`、`data.file_share`、`data.drag`、`data.dlp_access`、`data.clipboard`、`data.user_space_transfer`、`data.user_space_transfer_policy`。
  * 设备、媒体与调试：`media.window_capture`、`storage.volume`、`device.camera`、`device.printer`、`device.print_intercepted`、`device.usb_access_intercepted`、`device.serial_port_access`、`debug.hdc`、`debug.hdc_intercepted`。
  * 安全与应用拦截：`security.code_signature_missing`、`security.code_signature_abnormal`、`security.certificate`、`app.install_intercepted`、`app.uninstall_intercepted`、`app.update_intercepted`、`app.recover_intercepted`、`app.start_intercepted`。
  * 系统安全异常：`security.fs_mount_abnormal`、`security.driver_signature_abnormal`、`security.driver_mmap_abnormal`、`security.kernel_memory_abnormal`。
  * 企业管理：`edm.policy_read`、`edm.policy_change`、`edm.policy_operation`；只在 `type=0/1` 语义明确时细分，未知类型使用 `edm.policy_operation`。
* **无全局结果原则**: 不恢复已删除的全局 `result` 字段。认证结果、拦截状态和风险等级仅在对应事件字段明确存在时展示，不根据摘要关键词推断，不参与全局筛选或统计。
* **扩展流程**: 新增一个复用既有载荷结构的事件时，只需增加 Source 注册定义、Presentation 展示定义和对应样本测试；只有载荷结构确实不同才新增类别解析函数。新增普通事件不得修改 View、列表组件、详情组件、ViewModel 或 RDB 表结构。

  * Source 不再通过 `LogUtils` 输出完整 `content` / `metadata`，仅记录事件 ID、映射后的 `eventKey`、记录 ID、订阅或解析错误。

  * Store: `PREF_STORE_NAME_LOG = 'log_settings'`

- **异常兜底策略**:
  - 审计客户端不可用：`LogAuditSource.subscribe()` 返回 `unsupported`，采集器进入降级态。
  - 审计权限不足或订阅失败：返回 `permission_denied`，记录错误码，保留其他可用采集源。
  - 部分审计事件失败：返回 `partial`，`failedEventIds` 记录失败事件，成功事件继续工作。
  - 文件前缀过滤器不可用：文件事件不保留裸订阅，避免接收未限定路径范围的文件审计事件。
  - 审计日志事件订阅部分失败：`AUDIT` 对应的其它 `NotifyEvent` 沿用逐事件订阅策略，单个事件订阅失败只计入 `failedEventIds`；至少一个审计或崩溃来源可用时采集器进入 `partial` 降级态并保留成功事件。
  - 前台用户 ID 获取失败：回退到用户 `100` 构造前缀。
  - 审计事件未注册：不订阅；回调收到未注册 ID 时丢弃并记录一次必要 warning，不以通用原始 JSON 事件入库。
  - 已注册事件解析失败：保留能够确认的公共字段和稳定 `eventKey`；若连事件键或发生时间都无法确认，则丢弃，不写入存储。
  - 已知事件缺少可选字段：正常入库并省略对应字段，Presentation 只展示事件名称和现有公共字段，不显示占位值或原始载荷。
  - 扩展 JSON 解析失败或 `schemaVersion` 非目标版本：记录 warning，保留主记录的时间和一级类型，并使用对应的 `unknown` 业务键生成最小展示；不得解析或展示旧 `detailRows`，也不得以 `detail` 原文兜底。验收环境通过清理旧应用数据避免正常流程出现该降级态。
  - 初始化失败：返回 `storage_init_failed` 或 `query_failed`，页面保持未初始化态并记录错误日志。
  - 查询刷新失败：返回 `query_failed`，页面保持现有状态并记录错误日志。
  - 分页刷新失败：返回 `query_failed`，保留最近一次成功分页列表和页码状态，并记录错误日志，不向 UI 事件回调抛出未处理异常。
  - 时间范围筛选为空结果：保持正常查询成功状态，列表展示“无匹配结果”空态，不视为异常。
  - 开关机审计事件订阅失败：事件 ID 进入 `failedEventIds`，其它审计事件继续采集；不得回退为应用生命周期或公共事件推断。
  - 清理失败：返回 `clear_failed`，不主动清空 UI 列表。
  - 导出无数据：返回空数据结果，由 UI 给出提示。
  - 导入 Picker 取消：返回取消结果，页面保持当前状态。
  - 导入非 zip 外层文件：返回非法压缩包结果，不解压、不入库。
  - 导入解压失败：返回解压失败结果，保留已选目录中已写入文件但不写入日志数据库。
  - 导入规则解析失败：单文件或单行失败计入失败或丢弃统计，不影响其它文件继续导入。
  - 导入单文件 TaskPool 调度或返回失败：当前文件计入失败数量并继续后续候选文件，不回滚已成功文件。
  - 导入批次写入或导入中/最终容量维护失败：停止后续文件处理并返回 `save_failed`；已成功批次保留，重复导入时通过确定性 ID 和 `INSERT OR IGNORE` 跳过，不覆盖旧数据。
  - 系统日志文件名无法解析时间戳且读取文件 `mtime` 失败时：记录包含文件路径和异常原因的 warning，再回退到当前时间；不得静默改变导入记录时间。
  - 导入过期记录：按当前留存配置的自然日 cutoff 在入库前跳过，计入过期跳过统计，不进入维护服务入库链路。
  - 导入重复记录：按确定性 ID 跳过，不更新已有数据库记录。
  - 设置保存失败：保持脏状态，允许用户重试。

### 5.1 实施步骤与测试验收 (Implementation & Acceptance)

- **实施步骤**:
  - 涉及采集源、过滤条件、分页、详情、清理、留存配置、导出、RDB schema 或权限变化时，先更新本文档的目标范围、数据模型、状态流、职责边界、异常兜底和验收口径。
  - 涉及离线导入格式、规则端口、内核规则、hash 去重、压缩处理或导入结果口径变化时，先更新本文档。
  - 先在 `LogModels.ets` 建立 `eventKey`、`LogField`、可选 `rawPayload` 契约，并同步 Normalizer、Repository 序列化和导入规则；不得先改组件后让页面适配旧数据形态。
  - 再将 `LogAuditEventIds.ets` 与 `LogAuditSource.EVENT_IDS_BY_TYPE` 收敛为单一 `LogAuditEventRegistry`，使订阅、分类、解析和文件过滤从同一注册定义派生。
  - 按文件、账户、权限、电源和通用审计拆分类别解析器，删除 Mapper 内的中文标签、原始 JSON 详情行、递归 `content/metadata` 展开和完整载荷业务日志。
  - 建立 `LogEventDisplayRegistry`、`LogEntryPresentationMapper` 和展示模型，再调整列表及详情组件只消费展示契约。
  - 最后更新结构化 CSV 输出、UT、ohosTest/E2E 资产并进行真机逐类验收；确认无需兼容后，验收安装前清理旧应用数据。
  - 系统审计、崩溃、生命周期等输入先落在 Source / Collector / Maintenance 边界，再由 Repository 和 ViewModel 统一提供页面状态；页面不得直接解析审计事件或访问 RDB。
  - 新增或调整 `securityAudit.NotifyEvent` 时，必须先更新 Source 注册表，再更新确有差异的类别解析器和 Presentation 展示定义；普通事件扩展不得修改页面组件、ViewModel 或 RDB 表结构。
  - 开关机日志调整时，只能以真机安全审计配置确认的 `DEVICE_POWER_ON / DEVICE_POWER_OFF` 事件入库；不得用应用、进程、企业管理回调或公共事件推断设备开关机。
  - RDB 字段、索引、扩展 JSON 或留存策略变化时，需要同步清理策略、导出字段和历史数据处理口径。
  - 新增或调整审计权限时，同步 `entry/src/main/module.json5`、`hapsigner/UnsgnedDebugProfileTemplate.json` 并按签名流程重新生成 p7b。
- **测试覆盖**:
  - UT / Source 契约: 覆盖注册 ID 唯一性、每个订阅事件均有 `eventKey` 和解析器、文件过滤策略派生、API26 样本到 `LogEntry/LogField` 的映射、开关机时间与去重不回归。
  - UT / Presentation 契约: 覆盖八个一级类型及主要审计子域的列表标题、详情分组、中文标签、格式化、空值过滤、重复字段消除、未知业务键最小展示和长字段完整保留。
  - UT / 安全边界: 断言任何 `LogListItemViewData` / `LogDetailViewData` 不包含 `rawPayload`、`audit.content.*`、`audit.metadata.*`、“事件原始JSON”、转义 JSON 或以 `{` / `[` 开头的原始摘要；Source 日志不输出完整 `content/metadata`。
  - UT / Registry 完整性: 每个 Source 注册定义都有唯一 `eventId` 和非空 `defaultEventKey`，所有默认及解析器可产出的 `eventKey` 都有 Presentation 定义；新增普通定义后不需要修改 View 和 Components。
  - UT / Repository 与导出: 覆盖 `schemaVersion = 2` 序列化、损坏/旧版本扩展数据最小降级、结构化搜索摘要和 CSV 不导出内部原始载荷。
  - ohosTest: `entry/src/ohosTest/ets/test/simple/RouteAction.test.ets` 继续覆盖日志管理入口，并补充结构化列表、详情分组、长字段换行以及无原始 JSON 文案的页面契约。
  - E2E: `scripts/e2e/cases/logs/` 保留现有查询、筛选、统计、存储配置、导出和联动事件用例，扩展 `page_details.json` 覆盖具体事件标签、分组详情和原始数据不可见。
- **验收口径**:
  - 审计能力不可用或权限不足时，采集器进入可解释降级态，页面仍可查看已有日志和其它来源日志。
  - 当前 API26 SDK 中除高频 `NETWORK_TRAFFIC`、`NETWORK_CONN` 外的正式 `securityAudit.NotifyEvent` 应被明确归入 `FILE`、`ACCOUNT`、`PERMISSION`、`CRASH` 或 `AUDIT`；不得继续订阅不在正式枚举中的裸事件号，也不得将 `PROCESS_DEBUG_ABNORMAL` 归为崩溃。
  - 列表、详情和普通 CSV 导出只展示已注册业务字段，不显示原始 `content` / `metadata`、事件原始 JSON、递归字段路径、无法解析的对象或完整系统日志正文；缺少业务字段时只保留具体事件名称和可确认公共字段，不以原始载荷兜底。
  - 企业设备管理事件根据 `objectInfo` 和 `type` 展示已验证的中性中文语义。`disable_usb`、`usb_read_only`、`disabled_bluetooth`、`disable_wifi`、`disabled_printer`、`disable_microphone`、`disable_camera`、`disabled_hdc`、`disallowed_tethering`、`get_network_interfaces`、`disallowed_usb_devices`、`allowed_usb_devices`、`set_switch_status` 必须展示对应对象语义；未知对象显示原始对象值。仅 `type=0/1` 分别展示“读取/查询策略状态”“设置/变更策略状态”，其它值显示 `type=N`，不得推断用户来源或策略最终状态。无信息的 `targettInfo`、`extra`、固定 `subType` 不生成字段。
  - `FILE`、`ACCOUNT`、`PERMISSION`、`CRASH` 已有映射不得因新增 `AUDIT` 发生变化，未知且未列入订阅清单的裸事件 ID 仍不入库。
  - 文件操作日志的 `LogEntry.filePath` 与键为 `object.file_path` 的 `LogField` 必须来自同一文件审计路径解析结果；重命名事件必须展示目标/新路径作为“文件路径”，并额外展示“原文件路径”和“新文件路径”。样机中 `file_newpath=/data/service/el2/100/hmdfs/account/files/Docs/Download/333.txt`、`file_oldpath=/data/service/el2/100/hmdfs/account/files/Docs/Download/新建 文本文档.txt`、`file_path=''` 的事件，详情必须展示 `/storage/Users/currentUser/Download/333.txt`。
  - 已验证 API26 文件事件必须全部归类为 `LogEventType.FILE`，并复用 `FILE_PATH_PREFIX` 用户目录过滤；过滤上下文不可用、`addFilter` 不可用或挂载失败时，不得裸订阅该事件。
  - `FILE_SETMODE` 必须展示为“文件权限模式变更”；存在 `file_newmode` 时展示格式化后的新文件权限。`FILE_SETOWNER`、`FILE_SETEXTATTR`、`FILE_DELETEEXTATTR` 等事件的已验证字段同样遵循“有值才展示、无值不占位”的结构化详情规则，不向用户暴露 SDK 枚举拼接文案。
  - `FILE_COPY` 详情必须以 `file_newpath` 作为文件路径，并保留 `file_oldpath`。
  - 筛选、分页、详情和统计之间状态一致；分页失败保留最近一次成功列表，不向 UI 抛出未处理异常。
  - 留存配置保存失败保持脏状态，导出无数据给出明确提示，清理失败不主动清空 UI 列表。
  - RDB 查询、计数或统计失败时，刷新流程返回 `query_failed`，不得把异常查询结果展示为 0 条空列表。
  - 选择 zip 后，导入服务能自动使用应用私有临时工作根目录处理外层 zip、嵌套 zip 和内部 gz；导入命中内核规则的 `KERNEL` 记录，并将 `remoteLog/faultlogger` 下 appfreeze/jscrash/cppcrash 文件一文件一条导入为 `CRASH` 记录；UTF-8 中文内容跨读取块边界时不得乱码。
  - 准备任务只返回候选文件元数据，日志文件按顺序逐个提交 TaskPool；不得重新引入全包 `LogEntry[]`、全包 `newEntries[]` 或一次性全包 TaskPool 返回值。当前 254 MB 复现包和多个轮转文件组成的数 GB 日志包均不得出现 `failed to serialize result` 或 16 MB 序列化超限。
  - 单文件结果按 `1000 + 1000 + 余数` 分批处理；批内、跨批、跨文件和库内重复均不得覆盖已有记录。导入期间每累计约 10000 条允许执行不通知页面的容量维护，全部完成后只通知页面一次，最终记录数不得超过 `maxLocalEntries`。
  - 选择 zip 并进入导入处理后，“正在导入日志，请稍候...”加载弹框及模态遮罩必须覆盖整个应用窗口，包括左侧导航栏、顶部标题栏和日志内容区；底层页面不可操作，加载动画应持续正常运行。加载框宽度应与随后出现的成功/失败结果框一致，浅色模式使用清晰的深色主文字，深色模式使用清晰的浅色主文字。导入成功、返回失败、任务抛出异常或页面退出时，加载弹框必须关闭，且不得与后续成功/失败结果弹框重叠。
  - 导入服务不再弹出目录 Picker；导入成功、解析失败、入库失败或异常退出后，必须清理 `context.filesDir/log_import_tmp` 临时工作根目录；清理失败只记录错误日志，不覆盖导入主结果；下次导入前必须清理历史残留目录。
  - 重复导入同一日志包时，已有记录不更新，导入结果以重复跳过计数体现；已超过当前留存自然日 cutoff 的记录不入库，导入结果以过期跳过计数体现，新增条数只统计通过过期和重复过滤后提交入库的记录。
  - `SYSTEM` 类型可展示和筛选，导入 demo zip 后能看到命中白名单路径的系统日志记录；`remoteLog/hilog/hilog.*` 不产生系统日志导入数据。
  - 系统日志时间戳优先使用文件名时间，其次使用文件 `mtime`；`mtime` 读取失败时允许回退当前时间，但必须保留可诊断 warning。
  - 时间范围筛选默认“全部时间”不追加时间查询条件；选择最近 1 小时、最近 12 小时、最近 24 小时或最近 3 天时，列表、分页、过滤后数量、详情保留判断和导出结果均只包含 `timestamp >= startTimestamp` 的日志。
  - 普通应用冷启动不得产生 `POWER` / “设备启动”日志；真机重启后必须分别看到源事件 ID `0x16000002` 的“设备关闭”和 `0x16000001` 的“设备启动”，同一次真实事件仅保留一条；详情只展示结构化字段，不显示审计原始载荷。
  - 真机必须逐类检查文件、账户、权限、开关机、崩溃、系统、内核以及应用/进程/DNS/EDM/安全异常等审计子域；当前无法触发的事件使用已保存 API26 样本完成 Source 与 Presentation 契约测试，并在验收记录中明确未触发项。
  - 浅色和深色模式下，列表具体事件标签、详情分组标题和字段值均可读；长路径、错误消息和堆栈完整换行，不把弹窗撑出可视区域；空分组、空字段和重复字段不显示。
