## 1. 业务概述与对外接口 (Overview & Public Interfaces)
- **核心目标**: 提供企业管理员场景下的外设接口与有线网络总控、设备连接记录采集及单设备黑白名单策略管理能力。
- **入口路由 (Route Entry)**: `RouteIds.PERIPHERAL_MANAGE = 'peripheral-manage'`
- **对外暴露能力 (Public APIs)**:
  - `ApplicationRuntimeManager.ensureRuntimeServices()`
  - `PeripheralService`
  - `PeripheralConnectionRecordService`
  - `PeripheralDevicePolicyRepository`
- **业务边界**:
  - ✅ **有线网络管控**: 接口管控页在 Wi-Fi 下方展示独立“有线网络”项。通过 MDM Kit 枚举当前激活的有线网卡，禁用状态和写入结果均以系统策略为准，不持久化接口名或禁用状态；不与 `tethering` 网络共享策略混用。未连接有线网络、无法取得激活接口时不下发并提示“当前未连接有线网络，请连接”。
  - ✅ **包含**: USB、蓝牙、Wi-Fi、HDC、网络共享、打印机、麦克风、摄像头的接口管控；USB 接口应用侧默认管控策略；USB 存储访问策略；USB 插拔与蓝牙 ACL 连接记录采集、详情、导出、清理；基于 USB 策略状态库的 allow / deny 黑白名单策略；黑白名单 USB 设备按 SN 或 `VID + PID + description` 弱指纹维护应用侧逻辑策略状态，拔出后内部恢复系统允许策略但 UI 仍显示逻辑策略。
  - ❌ **不包含**: 企业管理员激活流程本身；防火墙、日志管理、身份鉴别、工具设置等非外设模块能力；未在当前代码中接入的其它外设类型运行时采集；USB Hub 拓扑节点（`baseClass = 0x09`）作为可展示或可管控的外设资产。

## 2. 状态与数据流 (Data Flow & State)
> **设计原则**: 单向数据流 (View -> ViewModel -> Service -> Repository/Storage)

- **核心业务状态 (Core Business State)**:
  - `InterfaceControlViewModel.state.ethernetDisabled`: 通过 MDM `networkManager.isNetworkInterfaceDisabledSync()` 回读的有线网卡接口禁用状态；与表示网络共享限制的 `networkDisabled` 相互独立，不在应用侧持久化。
  - `PeripheralViewModel.adminState: AdminActivationState`: 企业管理员激活状态及启用命令。
  - `PeripheralViewModel.reasonCode: string | null`: 最近一次外设业务失败原因码。
  - `PeripheralViewModel.currentTab: number`: 当前页签索引，取值由 `PeripheralTabIndexes` 统一定义，接口管控 / 设备连接记录 / 黑白名单分别保持 `0 / 1 / 2`。
  - `InterfaceControlViewModel.state: InterfaceControlStateModel`: USB、蓝牙、Wi-Fi、HDC、网络共享、打印机、麦克风、摄像头禁用状态，以及由 `USB_STORAGE_POLICY_OPTIONS` 映射的 USB 存储策略索引。`usbDisabled` 表示 restrictions `usb` 的设备级全局禁用真实状态；全局禁用优先于所有单设备策略，黑白名单保留原 `desiredPolicy` 但禁止编辑；`networkDisabled` 的页面文案保持“网络共享”，底层含义为 restrictions `tethering` 特性禁用状态，不表示有线网络接口禁用状态。
  - `InterfaceControlViewModel.processingKey: string`: 当前正在处理的接口或 USB 存储策略 key；接口 feature key 由 `PeripheralModels.ets` 中的 `PeripheralInterfaceFeatures` 统一定义，页面和组件不得直接依赖 `PeripheralService` 静态常量。
  - `PeripheralRecordViewModel.state.records: PeripheralConnectionRecord[]`: 连接记录列表。
  - `PeripheralRecordViewModel.state.connectionDetailDialog: ConnectionDetailDialogStateModel`: 连接详情弹窗选中记录和同设备历史。
  - `PeripheralPolicyViewModel.state.records: PeripheralPolicyRecord[]`: 黑白名单页展示列表；“当前策略”始终展示设备自身 `desiredPolicy` 对应的“允许接入 / 禁止接入”。`PolicyList` 的行身份同时包含逻辑策略、在线状态和可编辑状态，确保 USB 存储总策略变化时 ArkUI 不复用旧的锁定行。
  - `PeripheralPolicyViewModel.state.updatingKeys: string[]`: 正在更新策略的设备标识集合。
- **关键流转路径**:
  - `切换有线网络` -> `InterfaceControlTab` -> `PeripheralViewModel.ensureAdminReady()` -> `InterfaceControlViewModel` -> `WiredNetworkService`；每次通过 `getAllNetworkInterfacesSync()` 获取当前激活接口，逐个调用 `setNetworkInterfaceDisabledSync()`，随后通过 `isNetworkInterfaceDisabledSync()` 回读确认；未取得接口时返回专用原因码，任一接口失败时不提交成功状态。依赖 `ohos.permission.ENTERPRISE_GET_NETWORK_INFO`、`ohos.permission.ENTERPRISE_SET_NETWORK` 和企业管理员激活。
  - `接口开关失败回滚` -> 所有接口选择控件等待异步策略结果；成功后提交并展示新值，失败时保持 ViewModel 原状态并将下拉框恢复到操作前选项，同时展示对应失败提示。
  - `进入外设页面` -> `MainPage` 传入共享 `PeripheralViewModel` -> `PeripheralPage.initViewModel()` -> 页面本地 `interfaceControlReady=false`，接口内容区不创建控件且不显示加载动效 -> `PeripheralViewModel.initialize(context)` -> `PeripheralTraceMaintenanceService.initialize(context)` + `PeripheralDevicePolicyRepository.init(context)` -> `reloadAllData()` -> `InterfaceControlViewModel.reloadState()` 只读取接口策略状态，不主动改变 Wi-Fi / 蓝牙硬件开关，保留用户在系统设置中的手动关闭选择 -> 初始化结束后 `interfaceControlReady=true`，首次创建 `InterfaceControlTab` 并按已读取状态渲染；读取失败时沿用 ViewModel 默认值，设备连接记录 / 黑白名单 Tab 仍按原页面结构展示
  - `页面显示` -> `MainPage.handlePageActivated()` -> `ApplicationRuntimeManager.ensureRuntimeServices()` -> `RuntimeProducerAdapter + Pipeline + Consumers` -> `PeripheralTraceMaintenanceService.appendEntries()` -> `PeripheralTraceEntryRepository`
  - `切换接口或 USB 存储策略` -> `InterfaceControlTab` -> `PeripheralPage` -> `PeripheralViewModel.ensureAdminReady()` -> `InterfaceControlViewModel`；USB 接口由 `UsbGlobalPolicyService` 编排设备级全局 restrictions 策略，禁用前捕获真实在场 USB 设备并暂停 active deny，成功后补写 `usb_global_policy` 策略快照，恢复后重放在线显式 deny；其它接口或 USB 存储策略委托 `PeripheralService`；USB 存储策略切换成功后，由父级 `PeripheralViewModel` 使用 `InterfaceControlViewModel` 已提交的目标状态调用 `PeripheralPolicyViewModel.reloadRecords(...)`，避免 MDM 策略写入后的即时回读短暂返回旧值，并确保黑白名单页的可编辑状态立即一致；蓝牙全局禁用下发前读取本进程 ACL `CONNECTED` 当前连接缓存并预置待断开策略标记，下发失败或异常立即回滚标记，下发成功后由 `BluetoothPolicySnapshotTraceService` 对缓存设备补写 `policy_snapshot`，真实断开的策略判定不依赖快照写库结果；蓝牙重新启用成功后清空未消费标记；Wi-Fi / 蓝牙从禁用切回启用时，`PeripheralService` 在撤销 restrictions 策略后主动调用对应开启能力 -> `state 或 reasonCode 更新`
  - `USB 运行时事件进入` -> `PeripheralConnectionRecordRuntimeProducerAdapter` -> `PeripheralConnectionRecordPipelineImpl` -> `PeripheralConnectionRecordUsbConsumer` -> `解析 VID/PID/baseClass/SN/description` -> `UsbDeviceIdentityResolver` 生成强标识或弱指纹 -> `按统一 USB 名称规则生成 deviceName` -> `过滤 baseClass = 0x09 的 USB Hub 拓扑噪声` -> `UsbDevicePolicyStateService` 更新 `usb_device_policy_states` 在线态与逻辑策略 -> `按应用侧 USB 默认策略 / USB 存储策略 / 单设备逻辑策略 / 默认允许顺序生成基础判定` -> `connect 命中 deny 时下发 deny 并将 active_policy 标记为 deny` -> `disconnect 命中 active deny 时在无其它同 baseClass 在线 deny 设备的情况下内部恢复 allow 并将 active_policy 标记为 none` -> `插拔触发的内部恢复不补 policy_snapshot 或额外连接记录` -> `trace 落库`。
  - `蓝牙运行时事件进入` -> API 26 `connection.onAclStateChange()` 与 `connection.on('bondStateChange')` -> `PeripheralConnectionRecordRuntimeProducerAdapter` 把系统回调提供的设备地址、ACL 最终动作和 Bond 状态转换为独立内部事件 -> `BluetoothConnectionRecordCoordinator` 对每个 ACL 查询 `getPairState(deviceId)`，独立处理普通连接准入和同地址配对有效性判定，并维护 30 秒 Bond 会话及 BONDED 后 3 秒同地址 ACL 观察窗口 -> ACL 连接事实立即更新 `BluetoothRuntimeConnectionStore` -> `BluetoothDeviceNameResolver` 按系统即时查询、同地址缓存、事件时刻后 500 ms、1500 ms 补查的顺序解析名称 -> 普通设备在 ACL 最终态且有效名称命中后立即写入 trace；配对候选仅在同地址 ACL CONNECTED 与 BONDED 均成立且名称有效时写入。Bond 事件本身不生成记录，不收集其它新增地址，不合并不同地址，不增加蓝牙通用去重。
  - `黑白名单列表生成流` -> `USB 策略状态库变更` -> `PeripheralViewModel listener` -> `PeripheralPolicyViewModel.reloadRecords(...)` -> `PeripheralPolicyService.buildPolicyRecords(...)` -> `只读取 usb_device_policy_states` -> `PeripheralPolicyRecord[]` -> `PolicyList 展示 desired_policy 和 present 在线态`
- `单设备黑白名单更新流` -> `PolicyList.onPolicyChange` -> `PeripheralPage` -> `PeripheralViewModel.handlePeripheralPolicyChange()` -> `PeripheralPolicyViewModel.setDevicePolicy()` -> `UsbDevicePolicyStateService.setPolicy()` -> `在线设备先 dispatch 再保存 desired_policy/active_policy`；离线设备不允许修改 -> 用户主动策略变更成功后仍按现有规则补写 `policy_snapshot`，插拔触发的内部 allow 恢复不得补写 -> `PeripheralPolicyViewModel.reloadRecords(...)` 同时读取 USB 策略状态库和 EDM `getDisallowedUsbDevices()`，任一存在 deny/禁止类型时均令 `hasRestorableRecords=true` -> `PolicyList 与头部还原按钮刷新`。用户执行“还原策略”时，直接读取并移除 EDM 当前全部 `disallowed_usb_devices` 类型策略，再统一保存本地 `desiredPolicy=allow / activePolicy=none`；即使本地没有 deny 记录或 `activePolicy` 已错误收敛为 `none`，系统残留策略也必须可见、可清理。

黑白名单页按应用侧 USB 策略状态库展示逻辑策略，不再从连接记录反推候选，也不兼容旧 `device_policies` 单设备策略。USB 设备优先使用 SN 生成 `USB-SN:<serial>` 强标识；没有 SN 时使用公共事件 `description` 与 VID/PID 生成 `USB-WEAK:<vid>:<pid>:<descriptionHash>` 弱指纹。唯一标识生成由 `UsbDeviceIdentityResolver` 负责，RDB 仓储只按 fingerprint key 持久化，不耦合 fingerprint 规则。运行时首次发现 USB 设备连接时，默认 allow 不下发系统策略，但写入 desired_policy=allow / active_policy=none 并进入白名单；默认 deny 先同步下发，成功后才写入 desired_policy=deny / active_policy=deny，下发失败不新增黑名单记录。已有 allow 或 deny 逻辑策略不被运行时自动覆盖；已有 deny 命中时在 connect 阶段确保系统 deny 下发。USB detach 时若该设备 active_policy=deny，则在没有其它同 baseClass 且 present=1/active_policy=deny 的 USB 设备时内部恢复 allow；该恢复只修正系统状态和 active_policy，不补 policy_snapshot 或额外连接记录，UI 仍按 desired_policy 展示。离线 USB 设备 present=0 时黑白名单控件禁用。清空连接记录只清理 trace，不删除 USB 黑白名单状态；还原策略保留卡片和 fingerprint，将 desired_policy 恢复为 allow。USB Hub 不生成连接记录或名单状态；蓝牙设备不进入 USB 黑白名单。

### 2.1 USB 全局管控与黑白名单默认策略规格（已安装，待完整矩阵验收）

> 本节是当前 USB 总控与默认策略的权威规格。代码、UT、ohosTest 编译、主 HAP 构建、签名安装及核心禁用/恢复场景已完成；完整 2in1 USB 设备矩阵仍需按 Story 验收。
>
> 可执行 Story、任务拆分和完整验收清单见：`docs/superpowers/plans/2026-07-11-peripheral-usb-global-control-story.md`。

#### 2.1.1 规格与优先级

- 页面“USB 接口”改为 `@kit.MDMKit.restrictions` 的 `usb` 特性，`true` 表示设备作为 USB HOST 时整体禁止外接 USB DEVICE。
- `UsbGlobalPolicyService` 是全局 USB 切换的唯一编排边界，负责存储策略冲突检查、暂停/补偿设备级 deny、全局策略下发和恢复重放；接口 ViewModel 不直接依赖黑白名单 ViewModel 或设备策略状态服务。
- 全局 USB 禁用下发前必须通过 `usbManager.getDevices()` 捕获当前真实在场且非 Hub 的 USB 设备；全局禁用成功后为该捕获集合逐设备写入 `decision=deny`、`matchedPolicyKind=usb_disabled` 的策略变更记录。全局 USB 重新启用成功并完成在线 deny 重放后，再枚举当前真实在场设备并逐设备写入 `decision=allow`、`matchedPolicyKind=default_allow` 的策略变更记录。两类记录均使用 `source=policy_snapshot`、`action=discover`、`rawEventName=usb_global_policy`；不得从历史连接记录或本地黑白名单推断设备，捕获为空时不补记录。
- 三个 Tab 只通过父级 `PeripheralViewModel` 协调刷新，不允许页面或某个子 ViewModel 直接读取另一个子 ViewModel 的状态。黑白名单组件只消费 `PeripheralPolicyViewModel.state`，接口管控组件只消费 `InterfaceControlViewModel.state`。
- 全局 USB 状态以 `restrictions.getDisallowedPolicy(ADMIN_WANT, 'usb')` 回读结果为唯一真源，不新增本地全局状态持久化。
- 单设备显式策略继续由 `usb_device_policy_states.desired_policy` 保存，以 SN 强指纹为首选；无 SN 时沿用既有弱指纹规则。
- 有效策略优先级固定为：`全局 USB 禁用 > 已保存的单设备 desiredPolicy > usb_default_policy`。
- 全局禁用只覆盖当前有效结果，不改写各设备 `desiredPolicy`；恢复全局 USB 后，已下发/已保存的显式设备策略继续生效，未配置设备按独立默认策略处理。
- `peripheral_device_policy.usb_default_policy` 保留 allow/deny 语义，入口为“黑白名单 > USB 设备黑白名单默认策略”。该策略作用于新接入且尚无指纹策略的非 Hub USB 设备，不修改已有设备策略。切换默认值只保存配置，不立即下发策略，不批量创建或修改单设备记录。
- 新 USB 设备连接时，若已经存在该 SN/弱指纹策略，则完全忽略默认值；若不存在，默认 allow 时不下发系统策略但新增 allow 状态并进入白名单，默认 deny 时立即下发禁止，只有下发成功后才新增 deny 状态并进入黑名单。
- 默认 allow 表示“不采取禁止动作”，同时为已连接设备创建按 fingerprint 去重的白名单记录；默认 deny 只在新设备连接时触发下发，切换默认值本身不得枚举或修改当前设备。
- 默认 deny 下发失败时允许记录连接诊断，但不得把设备写成已成功生效的显式黑名单。
- 黑白名单页的默认策略不再使用独立悬浮卡片；它作为主名单卡顶部的紧凑策略栏，与表格/空态共用同一圆角、边框、阴影和 hover 位移动效，并继续复用 `AsyncSelectRow` 的 loading、置灰和失败回滚。

#### 2.1.2 状态模型

| 状态 | 真源 | 说明 |
|---|---|---|
| `usbGloballyDisabled` | restrictions `usb` 回读 | 设备级总控；不落 Preferences/RDB |
| `desiredPolicy` | `usb_device_policy_states` | 按 fingerprint 保存的设备期望策略；默认 allow 连接生成白名单记录，默认 deny 下发成功生成黑名单记录 |
| `activePolicy` | `usb_device_policy_states` | 当前是否真实下发设备级 deny；全局禁用期间应收敛为 `none` |
| `present` | USB 运行时状态 | 只对在线且显式 deny 的设备执行恢复重放 |

页面全局禁用时仍展示每台设备原 `desiredPolicy`，但选择器、USB 存储策略和“还原策略”按钮全部置灰，并展示“USB 已全局禁用，设备策略将在恢复后生效”。页面置灰不是唯一防线，ViewModel/Service 必须再次拒绝写操作。

USB 总接口开启但 USB 存储访问策略为 `DISABLED` 时，黑白名单中的 USB 存储设备仍保留原 `desiredPolicy`，当前策略列继续展示对应的“允许接入 / 禁止接入”，仅将单设备选择器置灰；不得允许用户提交必然被上层存储策略拒绝的 allow / deny 操作。后端继续保留冲突校验，绕过页面调用时返回“USB 存储当前已禁止访问，请先将 USB 存储访问模式设置为只读或读写”。非 USB 存储设备不受该规则影响。

USB 存储策略写入遇到 `9200010` 时，用户提示必须明确说明：USB 总接口当前已开启，失败来自设备黑白名单限制与 USB 存储访问模式冲突；不得笼统提示“需先启用 USB 设备”。黑白名单页必须把 EDM 残留类型策略计入可还原状态，确保提示指向的“还原策略”入口实际可用。

### 2.2 蓝牙连接记录入库规格

#### 2.2.1 事件来源与职责边界

- 蓝牙连接事实继续只来源于 API 26 `connection.onAclStateChange()` 的 `STATE_CONNECTED / STATE_DISCONNECTED` 最终态；`bondStateChange` 只提供配对过程上下文，`BONDING / BONDED / INVALID` 均不得直接生成连接或断开记录。
- 系统回调的 `deviceId` 按“系统提供的对端设备地址”使用和规范化，不宣称为可验证的硬件真实 MAC，不调用 `addPersistentDeviceId()`，不同地址不得按时间、名称或配对窗口永久合并为同一设备。
- `PeripheralConnectionRecordRuntimeProducerAdapter` 只注册、注销和转换系统事件，不持有配对状态机、名称重试或入库规则。
- 独立 `BluetoothConnectionRecordCoordinator` 是 Bond 会话、同地址 ACL 有效连接判定和名称准入的唯一 owner；Pipeline 只把蓝牙事件委托给 Coordinator，Consumer 只把已准入的 ACL 事件转换为 trace。
- 独立 `BluetoothDeviceNameResolver` 是名称解析顺序和定时补查的唯一 owner；`BluetoothRuntimeConnectionStore` 继续维护当前 ACL 连接事实与同地址有效名称缓存，不承担配对会话判断。

#### 2.2.2 运行时缓存与持久化边界

- `connectedSnapshots` 表示本进程收到的当前 ACL `CONNECTED` 事实。ACL connect 到达后无论名称是否可用都必须立即写入；ACL disconnect 到达后先读取快照名称，再移除当前连接。该缓存服务蓝牙禁用策略快照，不等同于用户可见 RDB 入库。
- `deviceNameCache` 只保存同一规范化地址的有效名称，不得保存通用占位名“蓝牙设备”，disconnect 后继续保留，不得跨不同地址复用。
- 只有两类 ACL 事件允许暂存在内存：名称即时查询和同地址缓存均未命中、正在等待名称补查的事件；以及 `getPairState(deviceId) = BOND_STATE_BONDING` 或地址明确命中当前配对目标、正在等待同地址 BONDED 的候选事件。不得暂存配对期间其它地址的普通 ACL，不得写 Preferences/RDB，不得改变 `occurAt`。
- RDB 只接收满足本节入库标准的事件。新蓝牙事件最终无有效名称时不得以任何通用占位名降级入库，不再执行历史占位名回填或兼容；升级验证前由测试人员清理旧数据库。

#### 2.2.3 名称解析顺序

名称解析固定以原始 ACL 事件时刻 `T` 为基准，顺序不得调整：

1. `T+0` 立即调用 `connection.getRemoteDeviceName(deviceId, false)`。
2. 即时查询为空或异常时，读取 `connectedSnapshots` 与 `deviceNameCache` 中同一规范化地址的有效名称；disconnect 必须在移除连接快照前完成该读取。
3. 仍无名称时在 `T+500 ms` 再调用一次系统名称接口。
4. 仍无名称时在 `T+1500 ms` 最后调用一次系统名称接口；该时间点是相对原始事件发生时间，不是在 500 ms 查询后额外等待 1500 ms。
5. 即时查询或同地址缓存取得有效名称时立即完成名称门槛，不等待 `T+500 ms / T+1500 ms`；补查任一次成功后也立即刷新 `deviceNameCache` 和同地址当前连接快照名称。名称门槛与连接有效性门槛均满足后立即准入；最终仍无有效名称时丢弃，不写 RDB。

有效名称必须满足 trim 后非空且不等于“蓝牙设备”。同一事件只允许存在一个补查任务；即时名称或缓存命中后立即清理任务状态；事件结算或 Coordinator stop 后必须取消剩余定时任务。Bond 失败、会话替换或超时只取消明确绑定到该配对会话的候选事件，不得取消其它普通 ACL 名称任务。

#### 2.2.4 配对会话、乱序与超时

- 收到 `BOND_STATE_BONDING(deviceId)` 后建立或刷新单一配对会话，记录规范化 `bondingDeviceId`。30 秒总超时从本轮首次 BONDING/明确 BONDING ACL 建立会话时开始计算，后续重复或换地址的 BONDING 只刷新目标地址，不重置或延长总超时，也不清除已由 `getPairState = BONDING` 明确识别的候选；最终仍只按 BONDED 返回的同地址结算。会话只约束地址等于 `bondingDeviceId`，或 ACL 到达时 `getPairState(deviceId)` 明确返回 BONDING 的候选；其它地址继续按普通 ACL 处理。
- 每个 ACL 到达时同步调用 `connection.getPairState(deviceId)` 补足 Bond/ACL 回调乱序：返回 BONDED 时可直接作为已配对证据；返回 BONDING 或地址命中当前配对目标时只暂存该地址最新 ACL 状态；返回 INVALID 且未命中配对目标时按普通非配对 BLE/经典蓝牙事件处理。
- 收到 `BOND_STATE_BONDED(deviceId)` 后记录该地址为唯一 `finalDeviceId`，但不直接生成连接记录；只允许同地址最新 ACL 状态为 CONNECTED 的候选继续准入。不同地址候选不与最终地址合并，也不生成记录。
- BONDED 已到但尚无同地址 ACL CONNECTED 时最多等待 3 秒；3 秒内同地址 CONNECTED 到达后进入名称准入。3 秒内仍未到达时结束本轮会话且不伪造连接记录；之后真实 ACL 到达时重新按其当时 `getPairState` 和普通 ACL 规则判断。
- 收到 `BOND_STATE_INVALID` 或 30 秒会话超时时，只取消本轮明确处于 BONDING/配对目标地址的候选；其它地址已经开始的普通名称补查和入库流程不受影响。
- 候选地址在 BONDED 前已经 DISCONNECTED，或 BONDED 时同地址最新 ACL 状态不是 CONNECTED，视为未形成有效连接，不写 connect/disconnect 记录。
- 系统返回不同地址时不做永久合并。配对期间出现的新地址只有在 `getPairState` 明确为 BONDING 或命中当前目标地址时才进入候选；不能仅凭“发生在 30 秒会话内”推断属于同一物理设备。

#### 2.2.5 蓝牙连接记录入库标准

一条蓝牙 ACL 事件只有同时满足以下全部条件才允许写入 RDB：

1. 动作为 `connect / disconnect` 且设备地址非空。
2. 名称已按“系统即时查询 -> 同地址缓存 -> T+500 ms -> T+1500 ms”取得有效值；即时查询或缓存命中时不得再因名称策略等待，但配对候选仍须满足下述同地址 BONDED 门槛。
3. 同一事件尚未成功写入或被丢弃，Coordinator stop 后不得继续写入。

在上述通用条件上，connect 再按连接类型分流：

- 普通非配对连接：当前没有命中同地址配对目标，且 `getPairState(deviceId) != BOND_STATE_BONDING`，ACL CONNECTED 与有效名称满足后立即入库，不等待其它 Bond 回调。
- 配对设备连接：必须同时具备同一规范化地址的 ACL CONNECTED 与 BOND_STATE_BONDED；两者顺序不限，只在两项证据均满足且名称有效后入库一次。

已准入连接后的 ACL DISCONNECTED 使用系统即时查询或同地址缓存解析名称并写断开记录。配对候选在 BONDED 前先断开时取消候选，不补连接或断开记录。普通 BLE、经典蓝牙和配对期间其它未命中目标的新增设备继续独立结算。蓝牙事件不做通用时间窗口去重，不因 `connectedSnapshots` 已存在同地址而吞掉原始回调。

### 3.2 能力域 F1：进入外设页并管控接口

- **用户故事**: 作为企业管理员，我希望进入外设管理页后看到系统真实管控状态，并对蓝牙、Wi-Fi、有线网络、HDC、网络共享、打印机、麦克风和摄像头执行启用/禁用，以便页面结果与 MDM 真实状态一致。
- **入口/触发**: `RouteIds.PERIPHERAL_MANAGE`；`PeripheralPage.initViewModel()`；接口行 `onSelected`。
- **前置条件**: 应用已按权限清单签名安装；读操作允许在管理员未激活时失败降级，写操作必须通过 `ensureAdminReady()`。
- **真源与事务边界**: 普通接口以 restrictions 回读为真源；有线网络以当前激活网卡的 `isNetworkInterfaceDisabledSync()` 回读为真源；页面只发送意图，只有 Service 层调用 MDM API。

**主流程伪代码：**

```text
FUNCTION enterPeripheralPage(context):
  interfaceControlReady = false
  DO NOT create InterfaceControlTab or any Select

  await PeripheralViewModel.initialize(context):
    destroy old listeners
    traceResult = await PeripheralTraceMaintenanceService.initialize(context)
    IF traceResult.failed:
      reasonCode = INIT_FAILED
      RETURN
    await PeripheralPolicyViewModel.initialize(context)
    await reloadAllData()
    register trace/default-policy/usb-policy-state listeners

  interfaceControlReady = true
  create InterfaceControlTab with InterfaceControlViewModel.state

FUNCTION reloadInterfaceState():
  read each restrictions feature independently
  read active ethernet interfaces and their disabled state
  read USB storage policy
  commit one observable state snapshot
  ON read exception:
    log error
    keep documented defaults; do not write any system state

FUNCTION toggleInterface(feature, targetDisabled):
  IF NOT ensureAdminReady(): RETURN ADMIN_REQUIRED
  processingKey = feature
  oldValue = state[feature]
  result =
    IF feature == ETHERNET:
      WiredNetworkService.setDisabledWithResult(targetDisabled)
    ELSE IF feature == USB:
      execute PERIPHERAL-002
    ELSE:
      PeripheralService.setInterfaceDisabledWithResult(feature, targetDisabled)
      // 对 WIFI/BLUETOOTH 从禁用切回启用时，Service 内部在撤销
      // restrictions 成功后继续执行 deviceSettings.setSwitchStatus(ON)

  IF result.failed:
    state[feature] = oldValue
    reasonCode = normalized failure reason
    RETURN failure

  state[feature] = targetDisabled
  reasonCode = null
  RETURN success
  FINALLY processingKey = empty
```

### 3.3 能力域 F2：USB 设备级全局禁用与恢复

- **用户故事**: 作为企业管理员，我希望一次禁用或恢复设备的 USB HOST 接入能力，同时保留每个 USB 设备的黑白名单意图，以便恢复全局 USB 后显式 deny 自动重放。
- **入口/触发**: 接口管控 Tab 的“USB 接口”选择器；`UsbGlobalPolicyService.setDisabled(disallow)`。
- **有效策略优先级**: `usbGloballyDisabled > desiredPolicy > usb_default_policy`。
- **事务不变式**: 全局状态只以 restrictions `usb` 为真源；全局禁用不改写 `desiredPolicy`；全局禁用期间 `activePolicy` 收敛为 `none`；恢复时只重放在线且 `desiredPolicy=deny` 的设备。

**禁用事务伪代码：**

```text
FUNCTION disableUsbGlobally():
  storagePolicy = readUsbStoragePolicy()
  IF read failed: RETURN READ_USB_STORAGE_POLICY_FAILED
  IF storagePolicy != READ_WRITE: RETURN SET_USB_INTERFACE_CONFLICT

  suspendResult = suspendActivePolicies():
    FOR EACH state WHERE present=true AND activePolicy=deny:
      dispatch allow for state.baseClass
      IF dispatch failed:
        restore every deny already suspended
        RETURN failure
      save activePolicy=none; keep desiredPolicy unchanged
  IF suspendResult.failed: RETURN USB_DISPATCH_FAILED

  connectedBeforeDisable = captureCurrentNonHubUsbDevices()
  globalResult = restrictions.setDisallowedPolicy(ADMIN_WANT, "usb", true)
  IF globalResult.failed:
    restorePresentDeniedPolicies()
    RETURN globalResult

  append policy_snapshot(connectedBeforeDisable,
    action=discover, decision=deny, result=BLOCKED,
    matchedPolicyKind=usb_disabled, rawEventName=usb_global_policy)
  // snapshot failure is diagnostic only; do not roll back successful global policy
  RETURN success
```

**恢复事务伪代码：**

```text
FUNCTION enableUsbGlobally():
  globalResult = restrictions.setDisallowedPolicy(ADMIN_WANT, "usb", false)
  IF globalResult.failed: RETURN globalResult

  replayResult = restorePresentDeniedPolicies():
    FOR EACH state WHERE present=true AND desiredPolicy=deny:
      dispatch deny for state.baseClass
      IF success: save activePolicy=deny
      ELSE: retain retry evidence and mark partial failure
  // partial replay does not lie about global state: USB is enabled, warning is logged

  wait 500ms
  devices = captureCurrentNonHubUsbDevices()
  IF devices is empty:
    wait additional 1000ms
    devices = captureCurrentNonHubUsbDevices()
  append policy_snapshot(devices,
    action=discover, decision=allow,
    matchedPolicyKind=default_allow, rawEventName=usb_global_policy)
  RETURN success
```

### 3.4 能力域 F3：USB 插拔、默认策略与连接记录

- **用户故事**: 作为企业管理员，我希望新 USB 设备接入时按默认规则立即判定，已识别设备始终遵循已保存意图，并保留可审计的连接/断开记录。
- **入口/触发**: USB attach/detach common event -> Producer -> Pipeline -> `PeripheralConnectionRecordUsbConsumer`。
- **识别规则**: 优先 `USB-SN:<serial>`；无 SN 时使用 `USB-WEAK:<vid>:<pid>:<descriptionHash>`；VID/PID 无效只可记录为未识别事件，不进入策略库。

**伪代码：**

```text
FUNCTION consumeUsbEvent(event):
  parsed = parse VID, PID, class, serial, description, names, occurAt
  IF parsed.baseClass == HUB(0x09): RETURN no record and no side effect

  identity = UsbDeviceIdentityResolver.resolve(parsed)
  IF event.action == CONNECT:
    IF identity exists:
      existing = policyStateRepository.find(identity.fingerprintKey)
      IF existing exists:
        desired = existing.desiredPolicy          // default never overwrites explicit intent
      ELSE:
        desired = defaultPolicyRepository.getUsbDefaultPolicy()

      IF usbStoragePolicy == DISABLED AND type == USB_STORAGE:
        skip device-level dispatch
        persist/update state without claiming active deny
        decision = deny by storage-level policy
      ELSE IF desired == deny:
        dispatchResult = dispatch deny by USB baseClass
        IF dispatchResult.success:
          upsert present=true, desiredPolicy=deny, activePolicy=deny
        ELSE IF existing does not exist:
          DO NOT create a successful blacklist state
      ELSE:
        upsert present=true, desiredPolicy=allow, activePolicy=none

    build CONNECT trace from actual decision/result/matchedPolicyKind

  ELSE IF event.action == DISCONNECT:
    IF identity exists:
      existing = find state
      IF existing.activePolicy == deny AND
         no other present active deny with same baseClass:
        dispatch allow internally
        IF success: activePolicy=none
      update present=false; keep desiredPolicy and lastSeenAt
    build exactly one DISCONNECT trace
    DO NOT append policy_snapshot for internal allow restoration

  append trace through PeripheralTraceMaintenanceService
```

### 3.5 能力域 F4：蓝牙 ACL/Bond 事件准入与记录

- **用户故事**: 作为安全审计人员，我希望只看到已发生且有可识别名称的蓝牙连接/断开，配对回调不伪造连接，乱序事件不丢失或合并其它设备。
- **入口/触发**: API 26 `onAclStateChange()` + `bondStateChange` -> Producer -> Pipeline -> `BluetoothConnectionRecordCoordinator`。
- **时间窗口**: 配对会话 30s；BONDED 后等待同地址 ACL 最多 3s；名称解析 T+0、同地址缓存、T+500ms、T+1500ms。

**伪代码：**

```text
FUNCTION handleBluetoothEvent(event):
  IF event.channel == BOND:
    IF state == BONDING:
      start/replace 30s session bound only to normalized deviceId
    ELSE IF state == BONDED:
      mark same-address session bonded
      IF same-address connected candidate exists: finalize candidate
      ELSE IF runtime store says same address connected: close session without synthetic record
      ELSE wait up to 3s for same-address ACL; timeout creates no record
    ELSE IF state == INVALID:
      cancel only candidates owned by this session; create no record
    RETURN

  IF event is not final ACL CONNECT/DISCONNECT: RETURN
  normalize system-provided device address
  immediateName = system query OR same-address cache
  IF CONNECT: runtimeStore.trackConnectedDevice(address, immediateName)
  IF DISCONNECT: obtain cached snapshot, then runtimeStore.forgetConnectedDevice(address)

  pairState = getPairState(address)
  IF DISCONNECT belongs to unresolved same-address pairing candidate:
    discard candidate; create no connect/disconnect record; RETURN

  name = resolve in order [T+0, same-address cache, T+500, T+1500]
  IF CONNECT AND (pairState==BONDING OR address matches current pairing target):
    hold candidate until same-address BONDED
    RETURN

  IF name invalid after retries: RETURN without RDB write
  persist final ACL event exactly as received
  DO NOT merge addresses and DO NOT apply generic time-window deduplication
```

```text
FUNCTION setDevicePolicy(fingerprint, targetPolicy):
  IF usbGloballyDisabled: RETURN USB_GLOBAL_CONFLICT
  state = repository.find(fingerprint)
  IF state missing OR state.present == false: RETURN DEVICE_OFFLINE
  IF state.type == USB_STORAGE AND usbStoragePolicy == DISABLED:
    RETURN USB_STORAGE_CONFLICT

  dispatchResult = dispatch targetPolicy by state.baseClass
  IF dispatchResult.failed: RETURN mapped reason without state commit
  save desiredPolicy=targetPolicy
  save activePolicy=(targetPolicy==deny ? deny : none)
  append user policy_snapshot for actual current VID/PID match only
  reload records and restorable state from local states + EDM
  RETURN success

FUNCTION setUsbDefaultPolicy(targetPolicy):
  IF usbGloballyDisabled: RETURN USB_GLOBAL_CONFLICT
  save peripheral_device_policy.usb_default_policy
  DO NOT enumerate current devices
  DO NOT modify existing device states
  DO NOT dispatch allow/deny

FUNCTION restoreAllPolicies():
  IF usbGloballyDisabled: RETURN conflict
  systemPolicies = usbManager.getDisallowedUsbDevices()
  FOR EACH distinct system USB type policy:
    remove system deny
    IF removal failed: RETURN failure and keep retry evidence
  FOR EACH local usb_device_policy_state:
    save desiredPolicy=allow, activePolicy=none; keep fingerprint and card
  reload records
  restorable = local has deny OR EDM still has deny
  RETURN success only when both sources contain no deny
```

### 3.8 Story 验收闭环与通过规则

- 每个 AC 只有在“业务结果、真源/持久化结果、失败可见性、指定证据”全部满足时才能判定通过。
- UT 中的 mock 成功不能代替 2in1 实机 MDM 结果；涉及 restrictions、USB 类型级策略、设备重枚举、蓝牙真实回调时，必须补实机证据。
- E2E 只证明页面入口、可见态和主交互契约；不得以文字节点点击成功代替真实 Tab 切换和 MDM 策略生效。
- 实机验收至少保留：设备型号/系统版本、管理员激活状态、操作前后页面截图、必要的脱敏日志、系统策略回读，以及 USB/蓝牙设备矩阵。
- 任一步只更新 UI 而未改变真源，或系统调用失败但页面显示成功，对应 Story 直接判定不通过。

### 3.10 逐 Story 开发实施卡

#### 3.10.1 执行规则与状态

本节用于直接拆开发任务。每次只领取一个 Story；如一次修改涉及多个 Story，必须分别记录实施结果和 AC 证据，不得用一个“整体通过”结论代替。

- `BASELINE`: 当前生产代码已有对应实现，后续开发应做差量修改，不重建平行链路。
- `UT-OK`: 已有主要 UT 入口，修改时必须更新或增补稳定 Story ID 用例。
- `UT-GAP`: 当前自动化不足以单独证明该 Story，进入开发时必须先补失败用例。
- `DEV-GAP`: 涉及真实 MDM/设备回调/多设备时序，必须补 2in1 实机证据才能交付。

**Definition of Ready (DoR)**：

1. 已确认目标 Story 及第 3.9 节对应 A/B/C 分支，不使用 Feature 作为模糊任务名。
2. 已说明是保持 As-Is 还是转为 To-Be；改变行为时先修改本文档的伪代码、真源、失败补偿和 AC。
3. 已确认下表的前置 Story/Task 已完成，系统 API 可在 UT 中 mock，需要实机时已准备设备矩阵。
4. 已在指定测试文件创建或确认 `U-<Story ID>-<分支>` 用例名，且在修改生产代码前能复现缺口或保护当前契约。

**Definition of Done (DoD)**：

1. 实施卡指定的生产代码责任点已完成，未将 MDM/RDB 细节泄漏到 Page/Component。
2. 第 3.9 节该 Story 的 A/B/C 分支全部通过，UT 用例名含 Story ID，需要的 E2E/DEV 证据已编号归档。
3. 失败分支已证明“不调用下游 / 不提交本地成功态 / UI 不伪装成功”，补偿分支已校验调用顺序。
4. 对应 UT、必要 ohosTest/E2E、`python scripts/check_docs_consistency.py` 和 `git diff --check` 已通过；无实机环境时不得将 `DEV-GAP` 标记为完成。

## 4. 模块结构与组件设计 (Module Components)

### 【核心层】(Core MVVM & Domain Layers)

#### 4.1 Model & Types (核心数据模型与类型)
* **核心实体与依赖路径**:
  * `PeripheralType`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 定义外设类型枚举。
    * **关键字段**: `USB_STORAGE / USB_CAMERA / USB_PRINTER / USB_HID / USB_OTHER / BLUETOOTH` (当前支持的外设类型)
    * **展示职责**: 设备类型、事件来源和动作文案由 `PeripheralRecordPresentationMapper` 输出，`PeripheralModels.ets` 不直接依赖模块字符串常量。
  * `UsbStoragePolicy`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 表示 USB 存储设备访问策略。
    * **关键字段**: `READ_WRITE` (读写), `READ_ONLY` (只读), `DISABLED` (禁止访问)
  * `PeripheralInterfaceFeature` / `PeripheralInterfaceFeatures`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 定义接口管控 feature key，作为页面、组件、ViewModel 和 Service 之间的共享领域常量。
    * **边界约束**: UI 层只引用模型常量，不直接引用 `PeripheralService.FEATURE_*`；`PeripheralService` 仅消费这些 key 并负责系统策略读写。
  * `PeripheralConnectionRecord`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 页面层连接记录展示模型。
    * **关键字段**: `deviceId` (设备标识), `action` (connect / disconnect), `result` (`SecurityEventResult`), `policyHit` (allow / deny / unknown), `effectivePolicyLabel` (列表策略展示), `matchedPolicyKind` (命中类型)
  * `PeripheralTraceRecord`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: RDB 持久化的外设运行记录模型。
    * **关键字段**: `recordId` (唯一记录键), `occurAt` (事件发生时间), `result` (`SecurityEventResult`), `source` (runtime_event / audit_event / policy_snapshot), `rawPayload` (原始事件快照), `usbPolicy` (USB 存储策略快照)
  * `PeripheralTraceQuery`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 外设 trace 仓库查询条件。
    * **关键字段**: `startTime/endTime`, `deviceId`, `keyword`, `deviceTypes/actions/decisions/results/sources`；分页由调用方通过仓库方法参数或上层 ViewModel 控制，不在 Query 模型中定义未消费字段。
  * `PeripheralTraceStats`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 安全总览卡片使用的外设 trace 汇总。
    * **关键字段**: `total`, `connects`, `disconnects`, `policyChanges`；安全总览外设卡片统计 `runtime_event` 的 connect / disconnect 和 `policy_snapshot` 的 discover，策略变更必须单独展示为策略变更次数，不得混入连接或断开次数。
  * `PeripheralDevicePolicySnapshotRequest`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 用户主动修改 USB 黑白名单后用于补写策略快照的输入模型；不是持久化黑白名单模型。
    * **关键字段**: `deviceId` (VID/PID 展示标识), `policy` (allow / deny), `updatedAt` (最后更新时间), `deviceName`, `deviceType`
  * `UsbDeviceIdentity`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: USB 设备唯一标识解析结果，隔离 fingerprint 生成规则和数据库持久化。
    * **关键字段**: `fingerprintKey` (SN 强标识或弱指纹), `fingerprintType` (`serial / weak`), `vendorId`, `productId`, `description`, `baseClass`, `deviceName`
  * `UsbDevicePolicyStateRecord`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: USB 黑白名单应用侧逻辑策略和当前系统下发态持久化模型。
    * **关键字段**: `fingerprintKey`, `desiredPolicy`, `present`, `activePolicy`, `lastSeenAt`, `updatedAt`；不保存连接记录 ID、lastError、lastDispatchAt 等可推导或诊断字段。
  * `PeripheralPolicyRecord`
    * **所在文件**: `entry/src/main/ets/models/PeripheralModels.ets`
    * **业务作用**: 黑白名单页组合展示模型。
    * **关键字段**: `deviceId` (候选设备键 / USB fingerprintKey), `lastSeenAt` (最近连接时间), `policyIndex` (由 `PeripheralPolicyOptionIndexes` 定义，`0` 允许 / `1` 禁止), `present` (是否在线), `editable` (是否允许修改)

#### 4.2 Service / Domain (领域业务层)
* **真实文件路径**: `entry/src/main/ets/services/peripheral/**`
* **核心业务用例 (Use Cases)**:
  * `PeripheralService.setInterfaceDisabledWithResult(feature, disallow)`: 下发非 USB 接口启用 / 禁用策略；`feature` 必须来自 `PeripheralInterfaceFeatures`。
    * **副作用**: 调用 restrictions 系统 API；USB 接口不再通过该路径调用 `restrictions.setDisallowedPolicy(..., 'usb', ...)`。网络共享通过 restrictions `tethering` 特性读写，不再使用 `networkManager.setNetworkInterfaceDisabledSync(...)` 禁用有线网络接口。Wi-Fi / 蓝牙从禁用切回启用时，在 restrictions 策略撤销成功后继续调用 `restoreEnabledInterfacePowerWithResult(...)` 主动开启硬件能力。
    * **失败策略**: 返回 `OperationResult`，保留错误码、管理员缺失标志和冲突 stage。
  * `PeripheralService.restoreEnabledInterfacePowerWithResult(feature)`: 对策略已启用的 Wi-Fi / 蓝牙执行启动恢复。
    * **副作用**: 统一调用 API 26 `deviceSettings.setSwitchStatus(...)`；Wi-Fi 和蓝牙均设置为 `SwitchStatus.ON`，允许用户后续手动关闭，不使用 `FORCE_ON`；依赖 `ENTERPRISE_MANAGE_SETTINGS`，其它接口直接返回成功。
    * **调用边界**: 仅在用户主动把 Wi-Fi / 蓝牙从禁用切回启用时调用；页面初始化和普通刷新不得调用，避免覆盖用户随后手动关闭硬件开关的选择。
    * **失败策略**: 返回 `OperationResult`，并通过 `turn_on_wifi` / `turn_on_bluetooth` stage 标识恢复失败；用户主动切换启用失败时按接口切换失败提示处理。
  * `PeripheralService.setUsbStoragePolicyWithCleanupResult(policy)`: 设置 USB 存储访问策略。
    * **副作用**: 调用 `usbManager.setUsbStorageDeviceAccessPolicy(...)`。
    * **失败策略**: 系统返回 `9200010` 时映射为 USB 冲突类失败；单设备 USB 存储策略被上层 `DISABLED` 阻断时，明确提示先将 USB 存储访问模式设置为只读或读写。
  * `PeripheralConnectionRecordService.queryRecords(filter?)`: 查询连接记录。
    * **副作用**: 读取 `PeripheralTraceEntryRepository`。
    * **失败策略**: 记录错误并返回空数组。
  * `PeripheralTraceMaintenanceService.initialize(context)`: 初始化 trace 仓库并对齐 retention / trim。
    * **副作用**: 初始化 RDB、删除过期记录、裁剪最大条数。
    * **失败策略**: 返回 `storage_init_failed`。
  * `PeripheralTraceMaintenanceService.appendEntries(records)`: 标准化并写入 trace。
    * **副作用**: `upsertBatch` 写入 RDB，随后执行容量与保留期整理并触发变更监听；不执行蓝牙历史占位名回填。
    * **失败策略**: 仓库未初始化返回 `not_initialized`，写入失败返回 `save_failed`。
  * `PeripheralConnectionRecordRuntimeProducerAdapter.start()`: 启动外设运行时事件订阅。
    * **副作用**: USB 继续订阅 attach / detach common event；蓝牙注册 API 26 `connection.onAclStateChange()` 与 `connection.on('bondStateChange')`，只转换系统提供的设备地址、ACL 最终动作、Bond 状态、cause 和发生时间。两个监听在 runtime stop 时按原 callback 注销，蓝牙关闭过程中不提前释放 ACL 监听。
    * **失败策略**: 无 context、`ACCESS_BLUETOOTH` 未授权、`GET_BLUETOOTH_PEERS_MAC` 未生效或任一蓝牙监听注册失败时记录降级状态并令 `bluetoothRuntimeEvents=false`，同时清理已经注册的另一监听；不回退旧 ACL common event 或私有 REALMAC 事件。
  * `PeripheralConnectionRecordPipelineImpl.push(event)`: 分发运行时事件并写入 trace。
    * **副作用**: USB 事件继续按既有 Consumer 和短时间去重链路处理；蓝牙 ACL/Bond 事件统一委托独立 `BluetoothConnectionRecordCoordinator` 结算，Pipeline 不持有配对状态、名称定时器或蓝牙准入规则；只有 Coordinator 返回的准入 ACL 事件才交给 Bluetooth Consumer 并调用 `PeripheralTraceMaintenanceService.appendEntries(...)`。
    * **失败策略**: trace 仓库未就绪时仅跳过需要落库的 trace record；Consumer 无法处理或写入失败时记录日志并返回未持久化结果。
  * `PeripheralConnectionRecordUsbConsumer.consume(event)`: 将 USB common event 转换为外设 trace。
    * **副作用**: 解析 payload 中的 VID/PID、baseClass、SN、description、设备名称和时间；USB 设备名统一按 `manufacturerName + productName` 优先，其次 `deviceName`，最后按 VID/PID 是否有效回退为“USB 设备”或“未识别 USB 设备”；`name` 字段不作为展示设备名来源，避免系统枚举名或泛化 payload 字段进入连接记录；对 USB Hub 拓扑节点（`baseClass = 0x09`）直接返回空消费结果；通过 `UsbDevicePolicyStateService` 更新 USB 状态库并按需下发 deny 或内部恢复 allow；USB_STORAGE 且 USB 存储策略为 `DISABLED` 时跳过该自动拉黑动作；最终生成 `PeripheralTraceRecord`。
    * **失败策略**: 不支持的 USB 事件、无法解析的事件或 USB Hub 拓扑噪声返回 `null`。
  * `UsbDeviceIdentityResolver`: USB 设备唯一标识解析服务。
    * **副作用**: 无；只根据事件或枚举数据生成 `UsbDeviceIdentity`，不读写数据库，不调用 MDM。
    * **失败策略**: VID/PID 无效时返回 `null`，调用方按未识别 USB 连接记录处理，不进入黑白名单策略状态。
  * `UsbDevicePolicyStateRepository`: USB 黑白名单策略状态 RDB 仓储。
    * **副作用**: 维护 `usb_device_policy_states` 表，字段限定为 fingerprint、VID/PID、description、baseClass、deviceName、desiredPolicy、present、activePolicy、lastSeenAt、updatedAt。
    * **失败策略**: RDB 未初始化或写入失败时返回失败并记录日志，不阻断连接记录基础落库。
  * `UsbDevicePolicyStateService`: USB 策略状态领域服务。
    * **副作用**: connect 时创建/刷新策略状态并按 desiredPolicy 下发 deny；disconnect 时按 activePolicy 和同 baseClass 在线 deny 设备数量决定是否内部恢复 allow；用户主动修改策略时拒绝离线设备修改；还原策略时通过 `getDisallowedUsbDevices()` 读取并移除 EDM 当前全部类型禁止策略，随后保留状态行、恢复 desired_policy=allow / active_policy=none。
    * **失败策略**: 策略下发失败时不更新 activePolicy 为目标状态；内部恢复失败只记录错误并保留 activePolicy，后续重试仍有依据。
  * `PeripheralPolicySnapshotTraceService`: 策略变更后的真实 USB 在场设备快照补偿服务。
    * **副作用**: 通过 `@kit.BasicServicesKit.usbManager.getDevices()` 枚举当前 USB 设备；设备类型只使用当前枚举结果中的 `USBDevice.clazz` 或 `configs[].interfaces[].clazz`，不使用策略记录、历史连接记录或审计事件兜底；设备名复用统一 USB 名称规则，不单独把 manufacturer、product 或 `USBDevice.name` 当作完整名称；过滤 USB Hub、无合法 VID/PID 和无有效 class 的设备；USB 默认策略、单设备策略或 USB 存储策略变更时为真实在场设备写入 `source = policy_snapshot`、`action = discover` 的 trace；单设备策略变更时仅在当前枚举结果中精确匹配同一 VID/PID 后写入快照；USB 存储策略变更时只针对当前枚举到的 USB_STORAGE 设备补写策略快照；快照写入委托 `PeripheralTraceMaintenanceService.appendEntries(...)`。
    * **失败策略**: 枚举失败、trace 仓储未就绪或写入失败只记录日志并返回失败结果，不回滚已经成功下发或保存的策略；枚举为空、Hub、无 VID/PID、单设备未匹配当前在场设备时返回成功且不写设备记录，避免伪造连接或在场数据。
  * `BluetoothRuntimeConnectionStore`: 蓝牙运行时连接事实与同地址名称缓存仓储。
    * **副作用**: 仅在本进程内按系统回调设备地址维护 ACL `CONNECTED` 当前连接和最近一次有效名称；connect 无论名称是否可用都更新当前连接快照，disconnect 先提供快照名称再移除当前连接；不持有配对会话或定时器，不持久化，不解析旧 common event payload。
    * **失败策略**: `deviceNameCache` 不保存“蓝牙设备”，不同地址不复用名称；进程启动前已存在的连接不会由 Store 自动推断或伪造。
  * `BluetoothDeviceNameResolver`: 蓝牙设备名称有限补查服务。
    * **副作用**: 按 `T+0` 系统即时查询、同地址连接快照/名称缓存、`T+500 ms` 系统补查、`T+1500 ms` 系统补查的固定顺序解析名称；查询成功后刷新 Store，同一事件只保留一个任务。
    * **失败策略**: 最终仍无有效名称时返回无名称结论，不生成“蓝牙设备”等通用占位值；stop、对应配对候选取消或事件结算时取消该事件剩余任务，不得由一个配对会话取消其它普通 ACL 名称任务。
  * `BluetoothConnectionRecordCoordinator`: 蓝牙 Bond/ACL 乱序关联与入库决策服务。
    * **副作用**: 维护 30 秒配对会话和 BONDED 后 3 秒同地址 ACL 观察窗口；始终先让 Runtime Store 更新 ACL 连接事实，并通过 `getPairState(deviceId)` 识别仅限同地址的配对候选。普通 ACL 在名称命中后立即交回 Pipeline；配对候选必须等到同地址 BONDED 才交回。
    * **失败策略**: 配对失败、候选先断开或会话超时只取消本轮明确绑定的配对候选；其它普通 ACL 及其名称补查不受影响。最终无有效名称的 ACL 不入库。不得收集其它新增地址、合并不同地址、生成合成 ACL 记录或执行通用蓝牙去重。
  * `BluetoothPolicySnapshotTraceService`: 蓝牙全局禁用策略变更后的真实连接快照补偿服务。
    * **副作用**: 接收禁用下发前从 `BluetoothRuntimeConnectionStore` 捕获并去重的当前连接快照；策略下发成功后对缓存设备写入 `source = policy_snapshot`、`action = discover`、`decision = deny`、`result = BLOCKED`、`rawEventName = bluetooth_global_policy`、`matchedPolicyKind = bluetooth_disabled` 的 trace，并从 Store 移除已处理的当前连接设备。
    * **失败策略**: 无有效名称的当前连接快照不得降级为“蓝牙设备”等通用占位名写入；无可写快照、trace 仓储未就绪或写入失败均不回滚已经成功下发的 restrictions 策略。策略快照不抑制后续真实 ACL `DISCONNECTED`，断开事件仍由蓝牙 Consumer 按普通运行时事件处理。
  * `PeripheralConnectionRecordBluetoothAclConsumer.consume(event)`: 将已规范化的蓝牙 ACL 内部事件转换为外设 trace。
    * **副作用**: 只消费 Coordinator 已准入且已携带有效名称的 ACL 事件，按允许接入语义生成 trace；不持有配对状态、名称重试、连接缓存更新、`linktype` 解析或时间窗口去重逻辑。
    * **失败策略**: 地址缺失、动作非法或有效名称缺失时返回 `null`，不得按“蓝牙设备”等通用占位名降级落库。
  * `PeripheralDevicePolicyDispatchService.dispatch(request)`: 将 USB 黑白名单策略下发到系统；USB 按设备类型映射为 MDM USB baseClass 下发。
    * **副作用**: 调用 `usbManager` 的 disallow API；USB 下发粒度为 `PeripheralType` 对应的 `UsbDeviceType`，不是 VID/PID 单设备。
    * **失败策略**: 检查全局接口禁用、USB 存储冲突和系统下发冲突，失败时返回 `PeripheralPolicyDispatchReason`。
  * `PeripheralDevicePolicyRepository.setUsbDefaultPolicy(policy)`: 保存 USB 接口应用侧默认管控策略。
    * **副作用**: 写入 `peripheral_device_policy` store 下的 `usb_default_policy` key，并触发 change listener。
    * **失败策略**: 记录错误并返回 `false`；默认读取值为 `allow`，避免升级后未知 USB 设备被默认拦截。
  * `PeripheralPolicyService.buildPolicyRecords(usbPolicyStates)`: 生成黑白名单页展示列表。
    * **副作用**: 纯内存转换；只接纳 `usb_device_policy_states`，不从连接记录反推候选，不叠加旧 `PeripheralDevicePolicyRepository.device_policies`。
    * **失败策略**: 跳过状态异常或无法展示的 USB 策略状态。
* **内部架构设计**:
  * **Repository**: `entry/src/main/ets/services/peripheral/connection-record/PeripheralTraceEntryRepository.ets` - 外设运行记录的 RDB 真源，表名为 `peripheral_trace_entries`。
  * **Repository**: `entry/src/main/ets/services/peripheral/device-policy/PeripheralDevicePolicyRepository.ets` - USB 默认管控策略的 Preferences 真源，是 `peripheral_device_policy` store 的唯一 owner；旧单设备策略键不再参与黑白名单链路。
  * **Mapper/Ports**: `entry/src/main/ets/services/peripheral/connection-record/PeripheralConnectionRecordPayloadUtils.ets` - USB 运行时 common event payload 提取工具；蓝牙链路不再使用该工具。
  * **Mapper/Ports**: `entry/src/main/ets/presentation/peripheral/PeripheralRecordPresentationMapper.ets` - 连接记录展示语义转换，包括设备类型、事件来源、动作和策略结果；时间格式委托公共 `DateTimeFormatUtils`，不依赖 ViewModel 目录或日志管理展示层。

设备连接记录的详细流程如下：

- `PeripheralConnectionRecordRuntimeProducerAdapter` 负责系统事件入口。USB 继续订阅 attach / detach common event；蓝牙同时使用 API 26 `connection.onAclStateChange()` 与 `connection.on('bondStateChange')`。Producer 显式把 `AclState.STATE_CONNECTED = 0` 映射为 `connect`、`AclState.STATE_DISCONNECTED = 1` 映射为 `disconnect`，并原样传递 Bond state/cause；不得复用旧 common event 数值规则。两个回调只在 runtime stop 时释放，蓝牙关闭过程不主动注销 ACL 回调。
- `PeripheralConnectionRecordProducerEvent.rawData` 继续只承载 USB `commonEventManager.CommonEventData`；蓝牙通过专用 `bluetoothAcl` 与 `bluetoothBond` 载荷传递系统设备地址、规范化动作/Bond 状态和采集时间，不伪造 common event。任一蓝牙回调注册失败时令 `bluetoothRuntimeEvents=false` 并清理已注册监听；不兼容旧公共事件、不订阅私有 REALMAC 事件、不通过 `addPersistentDeviceId()` 固化地址。
- `PeripheralConnectionRecordPipelineImpl` 负责事件接力。它绑定 context、挂载 Producer、连接 Consumers；USB 事件继续按 `deviceId + action + rawEventName` 做短时间去重，蓝牙 ACL/Bond 先委托 `BluetoothConnectionRecordCoordinator`，仅其准入事件进入蓝牙 Consumer。
- `PeripheralConnectionRecordPipelineImpl` 只处理外设连接记录采集与外设策略派生，不再挂载身份鉴别或 UKey 凭据生命周期 Consumer。UKey 插拔、首把绑定和 CustomAuth 凭据注册/删除已迁移到独立 `ukey/` 系统应用，由该应用自行订阅或探测 USB/DDK 状态。
- `PeripheralConnectionRecordUsbConsumer` 负责 USB 事件业务判定。它从 payload 中提取 VID/PID、baseClass、SN、description、设备名称和时间；USB 设备名与策略快照共用同一规则：`manufacturerName + productName` 两者同时存在时作为设备名，其次使用明确的 `deviceName`，否则按 VID/PID 是否有效显示“USB 设备”或“未识别 USB 设备”，不单独使用 manufacturer、product 或 `name` 作为完整设备名；若 `baseClass = 0x09`，该事件被识别为 USB Hub 拓扑噪声并直接返回 `null`，不进入 trace 落库、黑白名单候选或自动拉黑链路；其它 USB 事件继续推断 `PeripheralType`，并按应用侧 USB 默认策略、USB 存储禁止访问、USB 状态库 desired_policy、USB 存储只读、默认允许的顺序生成基础策略命中结果。
- `PeripheralConnectionRecordUsbConsumer` 对非 Hub USB connect 事件更新 USB 策略状态并执行首次连接默认策略：状态库不存在该 fingerprint 且默认 deny 时调用系统下发，成功后写入 deny 状态；默认 allow 时写入 allow 状态但不下发。
- `PeripheralConnectionRecordUsbConsumer` 对 USB_STORAGE 且 USB 存储总策略为 `DISABLED` 的连接事件不执行首次自动拉黑。该场景代表账户级 USB 存储禁止访问已生效，记录仍按 `usb_storage_disabled` 展示，不额外制造设备级 deny，避免后续恢复 USB 存储总策略或清空黑白名单时被设备级策略叠加阻塞。
- `PeripheralConnectionRecordBluetoothAclConsumer` 只消费 Coordinator 已准入且携带有效名称的系统设备地址和规范化最终动作，并按允许接入语义生成连接记录；名称查询、缓存、配对状态和连接事实更新均不在 Consumer 内实现。蓝牙设备不参与黑白名单候选构建，不读取本地单设备策略，不执行首次连接自动拉黑。
- 蓝牙链路不再读取 `linktype`，不按传输类型增加旧兼容过滤，也不对同地址、同状态增加通用时间窗口去重。应用卸载重装后从系统新回调地址记录，不迁移、不合并旧版本地址记录。
- `PeripheralTraceMaintenanceService` 负责落库前标准化。它补齐缺省字段、规范化 action / decision / source / result，并写入 `PeripheralTraceEntryRepository`，最后触发仓库变更通知；不再维护蓝牙历史占位名回填分支。
- `PeripheralConnectionRecordService` 负责页面查询。它从 `PeripheralTraceEntryRepository` 查询 runtime / audit 记录，并映射为 `PeripheralConnectionRecord[]`。

USB 冲突与单设备策略冲突是当前领域设计的关键规则：

- USB 接口总控使用 restrictions `usb` 的系统级全局禁用能力。USB 存储策略非 `READ_WRITE` 时阻止启用全局禁用并提示冲突，不自动覆盖用户存储策略。禁用前移除当前设备级 active deny、保留 desiredPolicy；恢复后重放在线显式 deny。全局禁用期间单设备策略和 USB 存储控件置灰，Service/ViewModel 同时拒绝写操作。
- USB 接口总控禁用和重新启用成功后都必须补写策略快照；禁用使用切换前捕获的当前设备，重新启用在恢复在线 deny 后于 T+0.5 秒枚举当前设备，若已取得有效设备则立即写启用快照；只有结果为空时才继续等到 T+1.5 秒补查一次。快照数据必须来自 `usbManager.getDevices()`，不能用历史连接记录、策略仓库或审计事件推断设备当前在场状态。快照动作为 `discover`，来源为 `policy_snapshot`，表示“策略变更时发现当前在场设备”，不表示真实插入连接。
- 蓝牙全局禁用保存成功后会补写策略快照，但快照数据只来自禁用下发前本进程自启动后收到的 ACL `CONNECTED` 当前连接缓存；不再调用 Classic profile 的 a2dp/hfp/hid/pan `getConnectedDevices()` 或 BLE `getConnectedBLEDevices()` 做前后枚举。审计事件 `disabled_bluetooth` 只用于日志管理表达策略变更发生，不进入外设连接记录的设备快照补偿；系统 profile 枚举、历史连接记录、配对记录或审计事件不得用于伪造设备 MAC 或名称。
- USB 存储策略保存成功后会补写当前 USB_STORAGE 设备的策略快照。快照数据同样必须来自 `usbManager.getDevices()` 当前枚举结果，action 固定为 `discover`，页面展示为“策略变更”；`DISABLED / READ_ONLY / READ_WRITE` 只影响策略结论、结果状态、USB 存储策略快照和命中类型，不伪装成真实连接或断开。没有当前在场 USB_STORAGE 设备时不补记录。
- `PeripheralService.setUsbStoragePolicyWithCleanupResult(...)` 设置 USB 存储策略时同样先读取当前 USB 策略快照，系统返回 `9200010` 时映射为 USB 冲突失败，而不是简单未知错误。
- 黑白名单策略不是“先保存本地，再尝试系统下发”。当前实现是 `PeripheralPolicyViewModel` 先调用 `PeripheralDevicePolicyDispatchService.dispatch(...)`，只有系统下发成功后才写入 `PeripheralDevicePolicyRepository`。
- 单设备黑白名单策略保存成功后只在 `usbManager.getDevices()` 当前枚举结果中精确匹配到同一 VID/PID，且能从当前枚举数据取得有效 class 时补写 `policy_snapshot`；未匹配或无有效 class 时只更新策略，不写当前设备快照。
- 首次连接自动拉黑同样遵循“先系统下发，再保存本地”。USB Consumer 只在非 Hub USB connect 事件、本地无既有策略且 `usb_default_policy = deny` 时触发自动 deny；已有 allow 或 deny 均不覆盖，已有 deny 命中不重复调用 `addDisallowedUsbDevices`，disconnect 事件不触发。USB Hub 拓扑节点（`baseClass = 0x09`）在策略判定前过滤，不触发自动 deny。USB_STORAGE 在 USB 存储总策略 `DISABLED` 下跳过首次自动拉黑，保留账户级禁用的连接记录语义。蓝牙 Consumer 不触发自动 deny。
- USB 黑白名单在本地按规范化 deviceId 管理和回显，但系统侧下发粒度是设备类型：`PeripheralDevicePolicyDispatchService.toUsbDeviceType(...)` 将 `PeripheralType` 映射为 MDM `UsbDeviceType.baseClass` 后调用 `usbManager`。当前代码没有按 VID/PID 对单个 USB 物理设备下发系统策略。因此 USB 首次连接自动拉黑可能影响同类 USB 设备，该误伤风险在当前规格中可接受。
- USB 黑白名单下发不再检查 restrictions 的 USB 全局禁用状态；USB 存储设备设置 allow 或 deny 前仍会检查 USB 存储账户级策略是否为 `DISABLED`。当 USB 存储总策略为 `DISABLED` 时，黑白名单仍按本地单设备策略展示，但 USB_STORAGE 单设备策略不允许继续下发 allow 或 deny，避免账户级禁止访问和设备级策略叠加。

黑白名单列表生成与策略下发的详细流程如下：

- `PeripheralPolicyService.buildPolicyRecords(...)` 只从 `usb_device_policy_states` 构建黑白名单页面记录，连接记录不再作为候选来源。
- `PeripheralPolicyService.normalizeDeviceIdForPolicy(...)` 只规范化 fingerprintKey，非 `USB-SN:` / `USB-WEAK:` 的旧 VID/PID 标识不再允许作为黑白名单修改入口。
- fingerprintKey 是黑白名单策略的本地业务 key，决定策略状态查询、策略保存和列表回显；其中 USB 的系统下发仍按设备类型/baseClass 执行。
- `PeripheralDevicePolicyDispatchService.dispatch(...)` 负责真实系统策略下发。USB 按 `PeripheralType` 映射的 `UsbDeviceType.baseClass` 下发。下发成功后才允许 `UsbDevicePolicyStateRepository` 保存 active_policy；下发失败时 active_policy 不更新为目标状态。
- USB 首次连接自动拉黑成功后，连接记录应展示为 deny / blocked，并保留“首次接入已自动加入黑名单”类详情。自动拉黑下发失败时，连接记录仍应落库，保留原策略判定结果，并在详情中追加失败原因，避免设备接入事实因策略下发失败而丢失。USB_STORAGE + USB 存储 `DISABLED` 场景不展示自动拉黑成功或失败语义，只展示 USB 存储已禁用。蓝牙连接记录不展示自动拉黑语义，策略结论记录为允许接入。
- USB_STORAGE + USB 存储 `READ_ONLY` 场景下若 USB 状态库 desired_policy=deny，连接事件应优先展示 `device_deny` 和已禁用，不得被 `usb_storage_read_only` 提前返回覆盖；断开事件和黑白名单同样以 desired_policy=deny 展示已禁用 / 禁止接入。

* **真实文件路径**: `entry/src/main/ets/viewmodels/peripheral/**`
* **状态分发逻辑**:
  * `PeripheralViewModel.initialize(context)`: 初始化 trace 维护服务和设备策略仓库，加载接口状态、连接记录与黑白名单，并注册 trace / policy listener。

界面展示设备时的策略判定由 ViewModel 组合链路保证：

- 连接记录页展示的是 trace 中已经落库的策略结果。`PeripheralRecordViewModel` 不会重新计算当前策略，而是直接展示 `PeripheralConnectionRecord` 中的 `effectivePolicyLabel`、`policyHit` 和 `matchedPolicyKind`。
- trace 变化后，`PeripheralViewModel.refreshTraceDrivenData()` 只调用 `PeripheralRecordViewModel.reloadRecords()` 刷新连接记录；黑白名单不再依赖连接记录候选，不因清空 trace 删除本地策略状态。
- 策略仓库变化后，`PeripheralViewModel.refreshPolicyDrivenData()` 只需要基于 USB 策略状态库重建黑白名单列表，不需要重新采集运行时事件。
- `PeripheralRecordViewModel.openConnectionDetailDialog(record)` 基于当前 `records` 构建同设备历史；`exportConnectionHistory()` 将当前连接记录导出为 CSV，表头、字段和 BOM 由公共 CSV 服务统一生成。
- 黑白名单页展示的是 `usb_device_policy_states` 中的 USB 逻辑策略状态。`PeripheralPolicyViewModel` 通过 `PeripheralPolicyService.buildPolicyRecords(...)` 将状态库记录转换为页面记录；蓝牙连接记录和历史 USB 连接记录不进入该列表。
- `PeripheralPolicyViewModel.setDevicePolicy(...)` 负责系统下发与本地状态更新；`clearAllPolicies()` 还原策略时只处理 USB 状态库记录，将卡片恢复为默认允许接入，不删除状态行，也不回滚或兼容旧 `device_policies`。

界面展示设备时的策略判定规则如下：

- `DeviceRecordList` 展示 `PeripheralConnectionRecord[]`，包含设备名称、设备类型、连接事件、策略、连接时间和详情入口。策略列由 `getPeripheralConnectionListPolicyLabel(record)` 生成：若 `record.effectivePolicyLabel` 有值，优先展示该值；若命中 `device_deny` 或 `policyHit === 'deny'`，展示禁用；否则展示启用。列表不重新计算当前策略。
- `ConnectionDetailDialog` 展示选中记录的关键信息和同设备历史连接记录。同设备历史由 `buildConnectionHistoryItems(records, selectedRecord)` 生成；“策略结论 / 执行策略 / 命中类型 / 结果状态”由 `PeripheralRecordPresentationMapper` 读取 trace 记录语义生成，不重新回查当前策略仓库。
- `PolicyList` 展示 `PeripheralPolicyRecord[]`，当前状态由 `policyIndex` 决定，索引取值来自 `PeripheralPolicyOptionIndexes` 并与 `PeripheralOptionStrings.POLICY_OPTIONS` 保持同序。该列表来自 USB 策略状态库，展示的是基于 fingerprintKey 合并后的业务记录，不直接展示原始事件 payload 中的设备标识。
- `PolicyList` 无候选设备时只展示常规字重的主空态文案，不再附加“重新插拔设备或检查账号权限”类兜底副标题。
- 用户在 `PolicyList` 中选择 allow / deny 后触发 `onPolicyChange`，由页面和 ViewModel 进入单设备黑白名单更新流；系统策略下发成功后再从 USB 策略状态库回读列表和头部按钮状态，不提前改写 `PeripheralPolicyRecord[]`。清空连接记录只清理连接记录 trace，在线和离线 USB 策略状态均保留；还原策略先移除 EDM 当前全部 USB 类型禁止策略，再保留 USB 状态库卡片并将已有记录恢复为 `desired_policy=allow / active_policy=none`。当前黑白名单存在 deny，或 EDM 仍存在 `disallowed_usb_devices` 残留时，头部还原策略按钮均可点击；两者都不存在时才置灰。

## 5. 异常处理与系统依赖 (Dependencies & Errors)

- **异常兜底策略**:
  - 企业管理员未激活时，`PeripheralViewModel.ensureAdminReady()` 返回 `PeripheralReasonCodes.ADMIN_REQUIRED`，页面统一提示先激活企业管理员。
  - USB 接口开关对应 restrictions `usb` 设备级全局策略；禁用前 USB 存储策略非 `READ_WRITE`、暂停 active deny 失败或系统策略冲突时，必须返回可区分的 USB 接口冲突/下发失败原因并保持操作前页面状态。独立 `usb_default_policy` 写入失败只影响新设备默认策略，不伪装为全局接口切换结果。USB 存储策略的系统冲突仍映射为 USB 冲突类 reasonCode，并通过 `resolvePeripheralReason(...)` 显示提示。
  - Wi-Fi / 蓝牙启用恢复失败时，用户主动切换启用返回接口切换失败且不更新本地开关状态；页面初始化只读策略，不触发硬件恢复。两类接口统一使用 API 26 `SwitchStatus.ON`，避免把“启用接口管控策略”扩大为强制用户不可关闭硬件；该恢复不涉及蓝牙单设备 MDM 黑白名单策略。
  - 单设备策略下发失败时，不更新 USB 状态库 active_policy 为目标状态；页面根据 dispatch 返回的冲突或失败原因提示用户。USB_STORAGE + USB 存储 `DISABLED` 时，allow / deny 两个方向都返回 USB 存储账户级冲突，不更新 active_policy。蓝牙设备不进入单设备策略下发链路。
  - USB 首次连接自动拉黑下发失败时，不更新 active_policy=deny，连接记录继续落库并在详情中追加失败原因；已有 allow 或 deny 逻辑策略时运行时自动拉黑跳过，不覆盖管理员决策；已有 deny 命中在 connect 阶段确保系统 deny 下发。USB Hub 拓扑节点（`baseClass = 0x09`）在策略判定前过滤，不进入失败提示、连接记录或本地策略保存链路。USB_STORAGE + USB 存储 `DISABLED` 场景同样不下发设备级 deny，避免账户级禁止访问和设备级 deny 叠加造成恢复链路阻塞。蓝牙连接记录始终按允许接入记录。
  - 蓝牙运行时权限被拒绝、对端设备地址权限未生效或 API 26 ACL/Bond 任一回调注册失败时，`bluetoothRuntimeEvents=false`；本次 runtime 启动不回退旧公共事件，后续由 runtime 重新启动再尝试注册。蓝牙关闭过程中不得注销既有 ACL 回调，以免丢失策略禁用触发的断开事件。
  - 蓝牙禁用策略快照无 ACL 当前连接缓存或快照写入失败时，不回滚已成功下发的蓝牙禁用策略；策略快照不抑制 ACL 断开记录，不使用设备名、系统 profile 枚举或历史记录模糊匹配来决定是否丢弃断开事件。
  - trace RDB 未初始化时，pipeline 在进入 consumer 前跳过当前运行时事件并记录日志，避免状态更新或策略下发先发生但 trace 无法落库；trace 写入失败时记录日志，不阻塞页面基本展示。
  - 导出和清理失败时，页面通过统一失败弹窗提示用户重试；CSV 导出写文件失败必须返回失败结果，不得留下部分成功状态。

- **验收口径**:
  - 企业管理员未激活时所有 MDM 写操作必须被阻断并提示；接口总控、USB 存储和单设备策略的冲突原因需要可见。
  - 外设页面首次进入或重新进入时，接口管控 Tab 在初始化结束前保持空白，不显示 `LoadingProgress`、骨架屏或新增错误界面，也不提前创建 `InterfaceControlTab` 或其内置 `Select`；初始化结束后再首次创建接口管控内容。读取成功时蓝牙、Wi-Fi、打印机等接口真实禁用状态必须正确显示；读取失败时允许沿用 ViewModel 默认“启用”和 USB 存储默认“读写”值。网络共享必须通过 restrictions `tethering` 特性回读，用户禁用网络共享后进入其它页面再返回外设管理时，选择框不得因有线网络接口状态而回到启用。
  - 蓝牙、Wi-Fi、有线网络、HDC、网络共享、打印机、麦克风和摄像头策略下发成功后，当前页面选择框必须立即展示新状态；下发失败时必须保持 ViewModel 原状态并恢复操作前选项。该验收不依赖离开页面后重新进入，也不得通过增加延时、业务镜像状态或强制重建页面实现。
  - Wi-Fi / 蓝牙仅在用户主动撤销禁用策略时触发一次 `SwitchStatus.ON` 恢复；页面初始化和刷新只读策略，不得主动开启硬件，避免覆盖用户的手动开关选择。
  - USB Hub 拓扑节点（`baseClass = 0x09`）不生成连接记录，不进入黑白名单候选，不触发首次自动拉黑，也不尝试单设备策略下发。
  - 非 Hub USB 首次连接在状态库无该 fingerprint 时读取 `usb_default_policy`：默认 allow 写入 allow 状态并进入白名单，默认 deny 下发成功后写入 deny 状态并进入黑名单。蓝牙只保留连接记录，不进入黑白名单。
  - USB 黑白名单策略状态必须按 SN 或 `VID + PID + description` 弱指纹维护；唯一标识解析逻辑不得耦合 RDB 仓储。黑名单 USB 插入后必须按逻辑策略下发 deny，拔出后在无其它同 baseClass 在线 deny 设备时内部恢复 allow；该内部恢复不得补连接记录或 `policy_snapshot`，UI 仍按 desiredPolicy 显示禁止。离线 USB 设备在黑白名单页不得修改策略；清空连接记录只清理 trace，不得删除在线或离线 USB 策略状态；还原策略不得删除黑白名单卡片，只能把已有 USB 状态恢复为默认允许接入。全部黑白名单均为允许接入时，还原策略按钮必须置灰不可点击。
  - USB 默认策略、USB 存储策略或单设备策略变更成功后，只对 `usbManager.getDevices()` 当前枚举到且非 Hub、具备合法 VID/PID 和有效 class 的 USB 设备补写 `policy_snapshot`；单设备策略必须精确匹配 VID/PID 才补写；策略快照 action 必须为 `discover`，不得写成 `connect` 或 `disconnect`；USB 存储策略快照只针对 USB_STORAGE，并通过 decision、result、usbPolicy、matchedPolicyKind 体现 `DISABLED / READ_ONLY / READ_WRITE`；枚举不到设备、未匹配当前设备或无有效 class 时不得生成设备快照。USB 运行时记录和策略快照的设备名必须共用统一解析规则：`manufacturerName + productName` 优先，其次 `deviceName`，最后兜底通用 USB 名称；不得使用 `name` 兜底。
  - 蓝牙全局禁用策略变更成功后，只对本进程 ACL `CONNECTED` 当前连接缓存中具备有效名称的系统设备地址补写 `policy_snapshot`；无名称快照仍可保留为禁用前连接事实，但不得降级为“蓝牙设备”等通用占位名写库。补写记录必须为 `source = policy_snapshot`、`action = discover`、`decision = deny`、`result = BLOCKED`、`rawEventName = bluetooth_global_policy`、`matchedPolicyKind = bluetooth_disabled`，页面展示为“策略变更”。随后同地址 ACL `DISCONNECTED` 仍按 Coordinator 入库标准结算，并继承一次 `deny / BLOCKED / 已禁用 / bluetooth_disabled` 状态。
  - 蓝牙采集必须同时注册 API 26 `connection.onAclStateChange()` 与 `connection.on('bondStateChange')`；不得回退普通 ACL common event、私有 REALMAC action、`linktype` 或 `isRetention`，不得把系统设备地址描述为已验证的硬件真实 MAC，不得增加通用蓝牙时间窗口去重或合并不同地址。
  - 蓝牙连接记录必须执行 2.2 节准入规则：Bond 不直接生成记录，但用于判定同地址配对候选是否形成有效连接；配对会话 30 秒超时；BONDED 后观察同地址 ACL 最多 3 秒且不伪造记录。普通 ACL 名称命中后立即入库；配对候选仅在同地址 ACL CONNECTED 与 BONDED 均成立后入库。名称固定按系统即时查询、同地址缓存、T+500 ms、T+1500 ms 解析。最终无有效名称时不进入 RDB，不新增“蓝牙设备”等通用占位记录；配对期间其它未命中目标且 `getPairState` 非 BONDING 的设备仍正常入库。
  - 同一系统设备地址后续解析到有效名称时，必须刷新本进程名称缓存、当前连接快照和历史同地址未命名记录；已有有效名称不得被覆盖。disconnect 必须先读取系统即时名称与同地址缓存，再移除当前连接快照。
  - USB_STORAGE + USB 存储 `DISABLED` 时，连接记录优先展示设备级禁止接入语义，allow / deny 两个方向均不下发单设备策略。
  - 运行时采集失败、蓝牙权限拒绝、API 26 ACL 回调注册失败或 RDB 写入失败时不阻断页面基本展示；状态上报必须反映真实可采集能力，导出和清理失败需保留可重试提示。
  - 外设连接记录和黑白名单导出同秒同名覆盖时，不得残留旧文件尾部内容。
  - 设备连接记录为空时，导出和清空按钮必须置灰且不可触发点击事件；黑白名单为空时，导出和还原策略按钮必须置灰且不可触发点击事件。黑白名单存在记录但全部为允许接入时，导出按钮保持可用，还原策略按钮继续置灰。页面事件处理函数必须保留空数据短路，异常触发路径不得弹出空数据失败提示或打开确认弹窗。
  - 设备侧连接记录契约不得把自定义 Tab 内部文字节点的点击结果作为页签切换结论；ohosTest 验证页签入口可识别，手工验收需实际切换至目标页签并确认“导出记录 / 清理记录”操作区可见。
  - 设备连接记录列表必须优先保证设备名称和设备类型可读：设备名列宽高于策略、连接时间等辅助列，设备名最多允许两行显示；设备类型列不得被压缩到标签文字截断，连接事件、策略、连接时间和详情操作列保持紧凑但不得出现文字重叠或按钮内容溢出。
